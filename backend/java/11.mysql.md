## 数值类型要点

- **UNSIGNED 只改取值范围，不改变占用字节**。`TINYINT` 和 `TINYINT UNSIGNED` 都是 1 字节。
- **`INT(11)` 这类显示宽度在 MySQL 8.0.17 起已废弃**，建表不要再写宽度；只有配 `ZEROFILL` 时才有意义（而 `ZEROFILL` 会隐式带上 `UNSIGNED`）。
- 溢出行为取决于 `sql_mode`：8.0 默认严格模式，超范围直接报 `Out of range value`，不会静默截断。
- 自增主键用 `INT UNSIGNED`（约 42 亿）通常足够；预估量级过亿且只增不删，再上 `BIGINT UNSIGNED`。
- **金额、精度敏感场景必须用 `DECIMAL`，不要用 FLOAT/DOUBLE**：二进制浮点无法精确表示 0.1，`0.1 + 0.2` 会得到 `0.30000000000000004`。
- `DECIMAL` 存储按「每 9 位十进制数字占 4 字节」分组，`DECIMAL(10,2)` 占 5 字节；`M` 最大 65，`D` 最大 30。
- `FLOAT(M,D)` / `DOUBLE(M,D)` 的写法同样在 8.0.17 起废弃，需要定点精度就用 `DECIMAL`。

## 文本与二进制类型要点

- **`CHAR`/`VARCHAR` 括号里是字符数，`TEXT`/`BLOB` 的限制是字节数**，别混。
- `CHAR` 定长，检索时**去掉尾部空格**；`VARCHAR` 保留尾部空格。适合场景：定长短值（性别、状态码、MD5、去横线 UUID）用 `CHAR`，长度差异大用 `VARCHAR`。
- `VARCHAR(65535)` 在 utf8mb4 下建表会报 `Row size too large`：65535 是「整行字节上限」，还要和同行其他列共享，InnoDB 单行实际约 8126 字节，超长值溢出到页外。
- `TEXT` 有字符集，比较排序按 `collation`；`BLOB` 是纯字节，无字符集，适合存加密数据、压缩包。
- `TEXT`/`BLOB` 不能设默认值（MySQL 8.0.13 之前），建索引必须指定前缀长度，如 `KEY idx_content (content(255))`。
- 大字段建议拆到独立子表，避免主表行溢出拖慢查询；**图片、文件不要存库**，存 URL。
- 单次写入受 `max_allowed_packet` 限制（默认 64MB），超大的 `LONGBLOB` 会被截断或报错，需要同时调服务端和客户端参数。

## 日期时间类型要点

- **`TIMESTAMP` 存的是 UTC 秒数**，查询时按会话 `time_zone` 转换；`DATETIME` 存字面值，不做时区转换。
- `TIMESTAMP` 只有 4 字节，**2038-01-19 03:14:07 UTC 之后写不进去**（2038 问题）；`DATETIME` 能撑到 9999 年。
- 自动维护时间列（最常用写法）：

```sql
create_time datetime not null default current_timestamp,
update_time datetime not null default current_timestamp on update current_timestamp
```

- 跨时区业务用 `TIMESTAMP` 更省心（自动换算）；只表示「墙上时间」的字段（生日、营业时间、预约时间）用 `DATETIME`。
- `TIME` 可以表示时长，范围能到 ±838 小时，不只是 0-24 点，适合存「耗时」。

```sql
create table user_demo (
  id          bigint unsigned not null auto_increment comment '主键',
  nickname    varchar(32)     not null default ''      comment '昵称',
  gender      char(1)         not null default '0'     comment '性别 0未知 1男 2女',

```


## 主键、唯一约束与外键

> 建表时写在列后面的那些关键字就是约束。它们决定「什么样的数据可以写进来」，索引则决定「查得多快」。这一节讲约束，下一节讲索引，两者经常一起出现（主键和唯一约束本身就是索引）。

### 1. 约束总览

| 约束 | 作用 | 一张表能有几个 | 是否自动建索引 |
| --- | --- | --- | --- |
| `PRIMARY KEY` | 唯一标识一行，非空 + 唯一 | 1 个（可复合） | 是，聚簇索引 |
| `UNIQUE` | 保证列值不重复，允许多个 NULL | 多个 | 是，唯一索引 |
| `FOREIGN KEY` | 保证子表的值在父表中存在 | 多个 | 子表列自动建普通索引 |
| `NOT NULL` | 禁止 NULL | 每列都可设 | 否 |
| `DEFAULT` | 不写该列时的默认值 | 每列都可设 | 否 |
| `CHECK` | 值必须满足布尔表达式 | 多个 | 否 |
| `AUTO_INCREMENT` | 自增（属性，不是约束） | 1 个，且必须是索引列 | 依赖索引 |

### 2. 主键 PRIMARY KEY

```sql
-- 单列主键（最常见）
create table t_user (
  id   bigint unsigned not null auto_increment,
  name varchar(32) not null,
  primary key (id)
) engine = InnoDB default charset = utf8mb4;

-- 复合主键：两列一起唯一，多用于关联表
create table t_user_role (
  user_id bigint not null,
  role_id bigint not null,
  primary key (user_id, role_id)
) engine = InnoDB default charset = utf8mb4;
```

- 主键 **隐含 NOT NULL**，写不写 `not null` 都一样。
- 一张表**只能有一个主键**，但主键可以是多列组成的复合主键。
- InnoDB 是**聚簇索引**表：主键索引的叶子节点直接存整行数据。所以主键不只是约束，还决定了数据的物理组织方式。

#### 2.1 自增主键

- `auto_increment` 只能用于整数列（`tinyint` / `int` / `bigint`），且该列必须是某个索引的**第一列**（通常是主键）。
- 一张表只能有一个自增列。
- **自增值不保证连续**：事务回滚、唯一键冲突、批量插入预分配、删除数据都会留下空洞。所以别拿自增 ID 当「总行数」或「顺序凭证」。
- 8.0 把自增计数器持久化到 redo log，重启后不再回退（5.7 重启可能回到 max(id)+1，导致 ID 复用）。
- `innodb_autoinc_lock_mode` 控制并发行为：8.0 默认 `2`（interleaved，并发最高、ID 可能跳号），5.7 默认 `1`（consecutive）。

#### 2.2 主键怎么选

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| 自增 `bigint` | 有序插入、页分裂少、索引小、 join 快 | 暴露业务量、分库分表需改造 | 绝大多数单库业务表 |
| `UUID` | 全局唯一、可离线生成 | 无序导致随机 IO 和页分裂、占 36 字节 | 分布式、多写入点 |
| 业务字段（手机号 / 身份证） | 天然唯一、少一次查询 | 可能变更、涉及隐私、字符串索引大 | 极少，通常只做唯一索引 |

- 分布式场景要用 UUID，优先存 `binary(16)` 而不是 `char(36)`；8.0 可用 `uuid_to_bin(uuid(), 1)` 把时间低位提前，让插入近似有序。
- **业务字段（手机号、邮箱、身份证）不要做主键**，改做主键 + 唯一索引：主键要稳定不变，业务字段会变。

#### 2.3 没有主键会怎样

- InnoDB 会退而选第一个「非空唯一索引」做聚簇索引；都没有就生成一个 6 字节的隐藏 `row_id`，全库共享一个计数器。
- **row 格式的 binlog 复制下，无主键表的 `update` / `delete` 会全表扫描**，主从延迟的常见元凶。
- 所以建表规范第一条：**每张表都必须有主键**。

#### 2.4 主键的增删改

```sql
-- 加主键（列必须非空且无重复）
alter table t_user add primary key (id);

-- 换主键：先删再加，自增列要先去掉 auto_increment
alter table t_user modify id bigint unsigned not null;
alter table t_user drop primary key, add primary key (id, tenant_id);
```

### 3. 唯一约束 UNIQUE

```sql
-- 列级写法
create table t_user (
  id    bigint unsigned not null auto_increment primary key,
  phone varchar(20) not null,
  email varchar(64) default null,
  unique key uk_phone (phone),
  unique key uk_email (email)
);

-- 复合唯一：同一租户内用户名不能重复，不同租户可以同名
alter table t_user add unique key uk_tenant_name (tenant_id, username);
```

- **唯一约束对 NULL 不生效**：`email` 列允许多行 NULL 共存，因为 `NULL = NULL` 结果是 UNKNOWN，唯一性检查不认为它们冲突。这是和主键最大的区别（主键不允许 NULL）。
- 同理，复合唯一索引里只要有任意一列为 NULL，这一行就不参与唯一性判断。
- 唯一约束会**自动创建唯一索引**，所以它既能保证唯一，也能加速等值查询。
- 命名规范：`uk_列名` / `uk_表名_列名`，方便报错时定位（`Duplicate entry 'x' for key 't_user.uk_phone'`）。

#### 3.1 唯一冲突的三种处理方式

| 写法 | 冲突时行为 | 注意 |
| --- | --- | --- |
| `insert into ...` | 直接报错 `Duplicate entry` | 最常用，让业务感知 |
| `insert ignore into ...` | 忽略该行，继续插其他行 | 其他错误（如超长）也会被降级成 warning，慎用 |
| `replace into ...` | **先删后插**（删除旧行再插入新行） | 会触发 delete 触发器、丢未指定的列、自增 ID 变化 |
| `insert ... on duplicate key update ...` | 执行 update 部分 | 推荐，语义明确，可只更新指定列 |

```sql
-- 幂等写入：存在则更新，不存在则插入
insert into t_user (phone, nickname, update_time)
values ('13800138000', '新昵称', now())
on duplicate key update nickname = values(nickname), update_time = values(update_time);
```

> `on duplicate key update` 只要命中**任意一个**唯一索引就会触发 update，表上有多个唯一索引时要小心更新到意想不到的行。

### 4. 外键 FOREIGN KEY

```sql
create table t_order (
  id       bigint unsigned not null auto_increment primary key,
  user_id  bigint unsigned not null,
  amount   decimal(12,2) not null default 0.00,
  key idx_user_id (user_id),
  constraint fk_order_user
    foreign key (user_id) references t_user (id)
    on delete restrict
    on update cascade
) engine = InnoDB default charset = utf8mb4;
```

#### 4.1 外键的前提条件

- 两张表都必须是 **InnoDB**（MyISAM 会解析但不生效）。
- 父表被引用的列**必须有索引**（通常是主键）。
- 子表列和父表列的**类型、符号（unsigned）、字符集、collation 必须完全一致**，否则建表直接报错。
- 外键列上 MySQL 会**自动建索引**（没有的话），所以不必手动再建。

#### 4.2 级联行为

| 选项 | 父表删除 / 更新时 | 说明 |
| --- | --- | --- |
| `restrict`（默认） | 拒绝操作 | 最安全，业务需先处理子表 |
| `no action` | 同 restrict | 标准 SQL 写法 |
| `cascade` | 级联删除 / 更新子表 | 方便但危险，容易误删一片 |
| `set null` | 子表外键列置 NULL | 该列必须允许 NULL |
| `set default` | 标准 SQL 有，InnoDB **不支持** | 别用 |

```sql
-- 删父表数据前先看有没有子表引用
select count(*) from t_order where user_id = 1001;
delete from t_user where id = 1001;  -- 有引用会报 1451
```

#### 4.3 外键的代价（为什么互联网公司普遍不用）

- **每次写入都要检查父表**，并在父表对应行上加共享锁，高并发下容易死锁、拖慢写入。
- **DDL 变麻烦**：改父表结构要先处理外键；分库分表后外键直接失效（跨库无法约束）。
- **数据迁移/导入顺序受限**，批量导入要先关掉检查。
- 阿里 Java 开发规范明确：**不得使用外键与级联，一切外键概念必须在应用层解决**。

**结论**：内部管理系统、单体小项目、数据一致性要求高的场景可以用外键，省心；高并发互联网业务、分库分表场景一律用应用层保证 + 普通索引，靠事务和幂等兜底。

#### 4.4 外键的查看与临时关闭

```sql
-- 查看外键
select constraint_name, table_name, column_name,
       referenced_table_name, referenced_column_name
from information_schema.key_column_usage
where table_schema = database() and referenced_table_name is not null;

-- 批量导入时临时关闭检查（只对当前会话生效，谨慎使用）
set foreign_key_checks = 0;
-- ... 导入 ...
set foreign_key_checks = 1;
```

### 5. CHECK 约束（8.0.16 起真正生效）

```sql
create table t_account (
  id      bigint unsigned not null auto_increment primary key,
  balance decimal(12,2) not null default 0.00,
  status  tinyint not null default 0,
  constraint chk_balance check (balance >= 0),
  constraint chk_status  check (status in (0, 1, 2))
);
```

- MySQL **8.0.16 之前会解析但直接忽略** `CHECK`，5.7 上写了等于没写，升级时要留意历史脏数据。
- `CHECK` 只约束新写入的数据，不会校验已有行；加约束前先清洗数据，否则 `alter table ... add constraint` 会失败。
- 枚举值约束还是建议用 `tinyint` + 应用层枚举，`CHECK` 改动要 DDL。

### 6. 约束的增删（ALTER 速查）

| 操作 | 语法 |
| --- | --- |
| 加主键 | `alter table t add primary key (id);` |
| 删主键 | `alter table t drop primary key;` |
| 加唯一 | `alter table t add unique key uk_col (col);` |
| 删唯一 | `alter table t drop index uk_col;` |
| 加外键 | `alter table t add constraint fk_name foreign key (col) references p (id);` |
| 删外键 | `alter table t drop foreign key fk_name;`（索引要另删） |
| 加检查 | `alter table t add constraint chk_name check (col > 0);` |
| 删检查 | `alter table t drop check chk_name;` |
| 改列非空 | `alter table t modify col int not null;` |
| 加自增 | `alter table t modify id bigint unsigned not null auto_increment;` |

### 7. 主键 / 唯一 / 普通索引 / 外键对照

| 维度 | 主键 | 唯一约束 | 普通索引 | 外键 |
| --- | --- | --- | --- | --- |
| 保证唯一 | 是 | 是 | 否 | 否 |
| 允许 NULL | 否 | 是（多行） | 是 | 取决于列定义 |
| 数量限制 | 1 个 | 多个 | 多个 | 多个 |
| 自动建索引 | 聚簇索引 | 唯一索引 | 本身 | 普通索引 |
| 主要目的 | 定位一行 | 业务唯一性 | 查询加速 | 引用完整性 |
| 高并发建议 | 必须 | 按业务需要 | 按查询需要 | 慎用 |

### 8. 易错点与工程建议

- 主键用业务字段（手机号、邮箱）—— 业务一变就要改主键，所有关联表跟着改，几乎不可维护。
- 以为自增 ID 连续 —— 回滚、冲突、删除都会跳号；要连续序号得用业务自己维护的序号表。
- `UNIQUE` 列写 `not null` 才发现「多行 NULL」问题 —— 需要「有值才唯一、没值随便」就保持可空，需要「必须有值且唯一」就加 `not null`。
- `replace into` 当 upsert 用 —— 它会先删整行，未指定的列会被重置为默认值，自增 ID 也可能变。
- 外键用 `cascade` 图省事 —— 删一个用户级联删掉订单、明细、日志，线上事故高发区。
- 5.7 上写了 `CHECK` 以为生效 —— 实际被忽略。
- 加唯一索引前没查重复数据 —— `alter table` 直接失败；先 `group by ... having count(*) > 1` 排查。

**dev / prod 提示**：dev 端把约束都建上（含外键、`CHECK`），让脏数据在开发阶段就暴露；prod 端按业务规模取舍——高并发表禁用外键与级联，用「应用层校验 + 事务 + 唯一索引兜底」，唯一索引是最后一道防线（防重复下单、重复注册），必须保留。大表加唯一索引先在从库/影子表验证重复数据，用 `ALGORITHM=INPLACE, LOCK=NONE` 的 online DDL，避开业务高峰并观察主从延迟。


## 索引

> 索引是 MySQL 性能的第一杠杆。这一节讲清「索引长什么样、怎么建、为什么失效、怎么设计」，与「where 子句 → 索引相关」互为补充：那里讲失效场景，这里讲原理和设计。

### 1. 索引的底层结构

- InnoDB 用 **B+ 树**：非叶子节点只存键值用于导航，叶子节点存数据并用双向链表相连，所以范围查询和排序很快。
- **聚簇索引（主键索引）**：叶子节点直接存整行数据，一张表只有一个。没有主键时用第一个非空唯一索引，再没有就用隐藏 `row_id`。
- **二级索引（普通索引）**：叶子节点存「索引列 + 主键值」。查非索引列时，先查二级索引拿到主键，再回聚簇索引取整行，这个过程叫**回表**。
- 一次查询回表次数多，随机 IO 就多，所以**覆盖索引**（查询的列全在索引里）非常重要。

### 2. 索引类型

| 类型 | 语法示例 | 说明 |
| --- | --- | --- |
| 主键索引 | `primary key (id)` | 聚簇索引，唯一且非空 |
| 唯一索引 | `unique key uk_phone (phone)` | 唯一 + 可查询 |
| 普通索引 | `key idx_name (name)` | 只加速查询 |
| 复合（联合）索引 | `key idx_a_b_c (a, b, c)` | 多列组合，遵循最左前缀 |
| 前缀索引 | `key idx_email (email(20))` | 只索引前 20 个字符，省空间 |
| 全文索引 | `fulltext key ft_content (content)` | 中文需 `ngram` 分词器，一般用 ES 替代 |
| 函数索引 | `key idx_lower ((lower(name)))` | 8.0.13+，表达式索引 |
| 生成列索引 | `year_col int as (year(ct)) stored, key idx_year (year_col)` | 5.7+，用生成列绕开函数失效 |

### 3. 建、查、删索引

```sql
-- 建表时建
create table t_demo (
  id   bigint unsigned not null auto_increment primary key,
  name varchar(32) not null,
  age  int not null default 0,
  key idx_name_age (name, age)
);

-- 建表后加
alter table t_demo add index idx_age (age);
create index idx_age on t_demo (age);   -- 等价写法

-- 查看
show index from t_demo;
show create table t_demo;

-- 删除
alter table t_demo drop index idx_age;
drop index idx_age on t_demo;
```

- 加索引在大表上是 DDL，8.0 支持 online DDL（`ALGORITHM=INPLACE, LOCK=NONE`），但仍会消耗 IO 并产生主从延迟；千万级表建议用 `gh-ost` / `pt-online-schema-change` 或低峰执行。
- 索引有名字，不写时 MySQL 自动按「列名」或「列名_2」生成，线上建议显式命名，方便后续删除。

### 4. 复合索引与最左前缀

索引 `idx_a_b_c (a, b, c)` 相当于同时拥有 `(a)`、`(a,b)`、`(a,b,c)` 三个索引，但**没有** `(b)`、`(b,c)`、`(c)`。

| 查询条件 | 能否用索引 | 用到几列 |
| --- | --- | --- |
| `where a = 1` | 能 | a |
| `where a = 1 and b = 2` | 能 | a、b |
| `where a = 1 and b = 2 and c = 3` | 能 | a、b、c |
| `where b = 2` | 不能 | 跳过了最左列 a |
| `where a = 1 and c = 3` | 部分 | 只用到 a，c 靠索引下推过滤 |
| `where a = 1 and b > 2 and c = 3` | 部分 | a、b 用于查找，c 只能靠索引下推过滤，不能用于排序 |
| `where a = 1 order by b, c` | 能 | 排序也能用索引（顺序一致） |
| `where a = 1 order by c` | 不能 | 跳过了 b |

- **范围条件会截断后续列**：`b > 2` 之后的 `c` 无法参与索引查找。
- 联合索引的列顺序原则：**等值条件在前，范围条件在后，排序列放最后**。
- 5.6+ 有**索引下推（ICP）**，`Extra` 显示 `Using index condition`，可以在存储引擎层用索引列先过滤，减少回表次数，但不能替代索引查找。

### 5. 覆盖索引

```sql
-- 索引 idx_name_age (name, age)
select name, age from t_demo where name = '张三';   -- Extra: Using index，不回表
select name, age, id from t_demo where name = '张三'; -- 也覆盖，二级索引叶子自带主键
select * from t_demo where name = '张三';            -- 要回表
```

- `EXPLAIN` 的 `Extra` 出现 `Using index` 就是覆盖索引，通常是最理想的状态。
- 高频查询尽量让它走覆盖索引：把 `select *` 改成只取必要列，或把常用列加进联合索引（注意索引体积）。

### 6. 索引失效清单

| 场景 | 反例 | 改写 |
| --- | --- | --- |
| 列上套函数 | `where year(create_time) = 2026` | 范围条件 `create_time >= '2026-01-01' and create_time < '2027-01-01'` |
| 列上做运算 | `where salary * 2 > 10000` | `where salary > 5000` |
| 隐式类型转换 | `where phone = 13800138000`（列是 varchar） | `where phone = '13800138000'` |
| 前导通配符 | `where name like '%张'` | 前缀匹配 `like '张%'`，或上全文索引/ES |
| 复合索引跳过最左列 | `where b = 2`（索引是 a,b） | 补上 a 或调整索引顺序 |
| `or` 连接无索引列 | `where a = 1 or b = 2`（b 无索引） | 拆 `union all`，或给 b 建索引 |
| 字符集/collation 不一致 | 两表连接列一个 utf8 一个 utf8mb4 | 统一字符集 |
| 区分度太低 | `where gender = 1` | 不单独建索引，作为联合索引的一部分 |
| 优化器判断全表更快 | 大范围 `where id > 1`（几乎全表） | 正常现象，不必强行 `force index` |

- `is null` / `is not null` 一般**可以**走索引，别被旧资料误导。
- `!=` / `not in` 通常走全表扫描，但不是绝对，取决于区分度和数据分布，看 `EXPLAIN` 为准。
- `like '张%'` 能走索引，`like '%张'` 和 `like '%张%'` 不能。

### 7. 索引设计原则

1. **区分度优先**：`select count(distinct col) / count(*) from t;` 结果接近 1 最适合建索引，低于 0.1 基本没意义（性别、状态、逻辑删除标记）。
2. **联合索引列序**：等值在前、范围在后、排序在后；把区分度高的列放前面。
3. **单表索引控制在 5 个以内**：每个索引都会让写入变慢（写放大）、占用空间、增加优化器选择成本。
4. **避免冗余索引**：有了 `(a, b)` 就不需要 `(a)`；有了主键就不需要再给主键建普通索引。
5. **长字符串用前缀索引**：`key idx_email (email(20))`，用 `count(distinct left(email, 20)) / count(*)` 验证选择性；前缀索引不能用于覆盖索引和排序。
6. **频繁更新的列慎建索引**：每次更新都要维护索引，且可能引起页分裂。
7. **区分「唯一索引」和「普通索引」的写入差异**：普通索引可以用 change buffer 延迟写入；唯一索引必须读磁盘页校验唯一性。写多读少且业务能保证不重复时，普通索引更快（但防重复还得靠唯一索引）。

### 8. 看懂 EXPLAIN

```sql
explain select id, name from t_demo where name = '张三' and age > 18;
explain format = json select ...;      -- 更详细
explain analyze select ...;            -- 8.0.18+，给实际执行时间
```

关键字段：

| 字段 | 关注点 |
| --- | --- |
| `type` | 访问类型，从好到坏：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `possible_keys` | 可能用的索引 |
| `key` | 实际用的索引，为 NULL 说明没走索引 |
| `key_len` | 用了联合索引的几列（越长通常越好，但要结合列类型算） |
| `rows` | 预估扫描行数，越小越好 |
| `filtered` | 过滤后剩余行数百分比 |
| `Extra` | 见下表 |

`Extra` 常见值：

| 值 | 含义 | 好坏 |
| --- | --- | --- |
| `Using index` | 覆盖索引，不回表 | 好 |
| `Using index condition` | 索引下推 | 较好 |
| `Using where` | 服务器层过滤（可能回表后才过滤） | 一般 |
| `Using filesort` | 额外排序，没用到索引顺序 | 差，大表要优化 |
| `Using temporary` | 用了临时表（group by / distinct / union） | 差 |
| `Using join buffer (hash join)` | 被驱动表无索引，用哈希连接 | 一般，能加索引更好 |
| `Using MRR` | 多范围读，减少随机 IO | 好 |

- `type = ALL` 且 `rows` 很大，就是全表扫描，优先加索引或改写 SQL。
- `key_len` 能反推联合索引用了几列：`int not null` 占 4 字节（可空再 +1）；`varchar(20)` 且字符集 utf8mb4 时占 20×4 + 1（长度）+ 1（可空标志），约 82 字节。

### 9. 索引维护

- 索引统计信息不准会导致优化器选错索引：`analyze table t;` 重新采样。
- 大量删除后表空间不回收：`optimize table t;`（本质是重建表，会锁表，用 `gh-ost` 更稳）。
- 索引碎片、页分裂严重时，重建索引（`alter table t drop index ... , add index ...`）能回收空间。

### 10. 易错点与工程建议

- **索引不是越多越好**：5 个以上就要审视，写入性能和空间都会变差。
- **联合索引顺序写反**：`(status, create_time)` 和 `(create_time, status)` 差别很大，按「等值在前、范围在后」定。
- **以为建了索引就一定走**：区分度低、数据量小、范围过大时优化器会放弃索引，以 `EXPLAIN` 为准。
- **`select *` 破坏覆盖索引**，高频查询明确列名。
- **在索引列上套函数**是最常见的失效原因，`where date(create_time) = curdate()` 一定要改成范围。
- **字符集不一致**导致连接或查询隐式转换，索引静默失效，建库统一 `utf8mb4`。
- **大表直接 `alter table add index`** 可能锁表/主从延迟，用 online DDL 或第三方工具。
- **索引名重复**在不同表上不冲突，但同一张表内必须唯一，规范命名 `idx_` / `uk_` / `fk_` 前缀。

**dev / prod 提示**：dev 端打开慢查询日志（`slow_query_log = 1`、`long_query_time = 0.5`），每条新 SQL 上线前跑一遍 `EXPLAIN`，确认 `type` 不低于 `range`、没有 `Using filesort`；prod 端索引变更走灰度：先在从库建、观察主从延迟，再切主库，大表用 `gh-ost`，并保留回滚脚本（`drop index`）。定期用 `performance_schema` 或慢日志找出「扫描行数远大于返回行数」的 SQL，这类才是索引优化的重点。

## where 子句

`where` 紧跟在 `from` 之后，用于过滤行。下面是 `where` 子句中经常使用的运算符。

### 比较运算符

| 运算符 | 说明 | 示例 |
| --- | --- | --- |
| `>` `<` `>=` `<=` | 大于、小于、大于等于、小于等于 | `salary > 5000` |
| `=` | 等于（SQL 是单等号，不是 `==`） | `id = 1` |
| `<>` / `!=` | 不等于，`<>` 是 SQL 标准，`!=` 为 MySQL 兼容写法 | `status <> 1` |
| `BETWEEN x AND y` | 落在闭区间内，等价于 `>= x and <= y` | `salary between 5000 and 10000` |
| `IN (set)` | 等于列表中任意一个值 | `id in (100, 200)` |
| `NOT IN (set)` | 不等于列表中任何值 | `id not in (1, 2)` |
| `LIKE 'pattern'` | 模糊查询，`%` 匹配任意长度字符，`_` 匹配恰好一个字符 | `name like '张%'` |
| `NOT LIKE 'pattern'` | 不匹配该模式的模糊查询 | `name not like '%测试%'` |
| `IS NULL` / `IS NOT NULL` | 判断是否为空值 | `email is null` |

### 逻辑运算符

| 运算符 | 说明 | 示例 |
| --- | --- | --- |
| `AND` | 多个条件同时成立 | `salary > 5000 and dept_id = 10` |
| `OR` | 多个条件任一成立 | `dept_id = 10 or dept_id = 20` |
| `NOT` | 条件不成立（取反） | `where not (salary > 100)` |

### 易错点

- **优先级 `NOT` > `AND` > `OR`**：混用时一律加括号。`where a = 1 or b = 2 and c = 3` 会被解析成 `a = 1 or (b = 2 and c = 3)`，与直觉不同。
- **NULL 三值逻辑**：任何值与 `NULL` 比较结果都是 `UNKNOWN`，既不被 `where` 选中，取反后也选不中。
  - `= null` / `!= null` 永远不成立，必须用 `is null` / `is not null`。
  - `not in (...)` 的列表里只要含 `NULL`，整个条件一行都不返回 —— 最经典的坑，改用 `not exists` 或先滤掉 NULL。
  - `count(列)` 会跳过 NULL，`count(*)` 不会。
- **`BETWEEN` 是闭区间，且小值必须在前**：写成 `between 10000 and 5000` 不报错但恒为空集。用在 `DATETIME` 上更要小心时分秒：`where create_time between '2026-11-01' and '2026-11-06'` 会漏掉 6 号 00:00:00 之后的数据，应改用左闭右开 `>= '2026-11-01' and < '2026-11-07'`。
- **SQL 执行顺序**：`from` → `join/on` → `where` → `group by` → `having` → `select` → `distinct` → `order by` → `limit`。所以 `where` 里**不能用 `select` 定义的别名**（此时别名还没生成），别名只能在 `having`、`order by` 里用。

### 索引相关（性能）

- 前导通配符 `like '%xxx'` 用不上 B+ 树索引，必然全表扫描；`like '张%'` 可以走前缀索引。大表模糊搜索应上全文索引或 Elasticsearch。
- **不要对列做函数或运算**：`where year(create_time) = 2026`、`where salary * 2 > 10000` 都会让索引失效，改写成范围条件 `where create_time >= '2026-01-01' and create_time < '2027-01-01'`。
- 隐式类型转换同样让索引失效：字符串列写成 `where phone = 13800138000`（没加引号）会触发全表扫描，值一律按列类型加引号。
- `in` 列表别塞几百上千个值，超长改成 `join` 临时表或子查询。
- `or` 两侧只要有一列没索引，整条语句就退化为全表扫描，必要时拆成 `union all`。

### 示例

```sql
-- 区间 + 排序
select id, name, salary from emp
where salary between 5000 and 10000
order by salary desc;

-- AND / OR 混用必须加括号
select * from emp
where dept_id in (10, 20, 30)
  and (salary > 8000 or job_level >= 5);

-- 模糊查询：三种通配符形态
select * from emp where name like '张%';       -- 张开头，可走索引
select * from emp where name like '%工程师%';  -- 包含，全表扫描
select * from emp where name like '张_';       -- 张 + 恰好一个字

-- NULL 判断（不能用 = null）
select * from emp where commission is null;
select * from emp where commission is not null;

-- NOT 与优先级
select * from emp where not (salary > 100);

-- 日期区间：左闭右开，避免漏掉当天数据
select * from emp
where create_time >= '2026-11-01' and create_time < '2026-11-07';
```

## 函数

### 一、聚合（统计）函数

对「一组行」做计算，返回**一个值**，常与 `group by` 搭配。

| 函数 | 说明 | 示例 |
| --- | --- | --- |
| `COUNT(*)` | 统计所有行数，不跳过任何行 | `select count(*) from emp` |
| `COUNT(列)` | 统计该列**非 NULL** 的行数 | `select count(commission) from emp` |
| `COUNT(DISTINCT 列)` | 去重后计数，跳过 NULL | `select count(distinct dept_id) from emp` |
| `SUM(列)` | 满足 `where` 条件的行的总和 | `select sum(salary) from emp` |
| `AVG(列)` | 平均值，等价于 `SUM(列)/COUNT(列)` | `select round(avg(salary), 2) from emp` |
| `MAX(列)` / `MIN(列)` | 最大 / 最小值，也可用于日期和字符串 | `select max(create_time) from emp` |
| `GROUP_CONCAT(列)` | 把组内多行拼成一个字符串 | `group_concat(name order by salary desc separator ',')` |

```sql
-- count 三种写法
select count(*)              as all_rows,      -- 含所有行
       count(commission)     as has_commission,-- 跳过 commission 为 NULL 的行
       count(distinct dept_id) as dept_cnt     -- 去重计数
from emp;

-- sum 返回满足 where 条件的行的和
select sum(salary) from emp where dept_id = 10;
```

**要点**

- `count(*)` 统计所有行；`count(列名)` **跳过该列为 NULL 的行**，两者结果在存在 NULL 时不一样。
- `count(1)` 与 `count(*)` 在 InnoDB 里被优化成同一执行计划，没有性能差异，**统一写 `count(*)` 即可**（SQL 标准写法）。
- `sum` / `avg` / `max` / `min` 都会**自动跳过 NULL**；但 `avg` 的分母是 `count(列)` 而不是 `count(*)`，有 NULL 时结果会和你手算的不一样。
- 空结果集或全为 NULL 时：`count` 返回 **0**，其余聚合函数返回 **NULL**。业务层要 0 值就用 `ifnull(sum(salary), 0)` 兜底。
- **聚合函数不能写在 `where` 里**（`where` 在分组前执行），过滤分组结果用 `having`。
- MySQL 8.0 默认开启 `ONLY_FULL_GROUP_BY`：`select` 里只能出现 `group by` 的分组列和聚合函数，否则报 `isn't in GROUP BY`。

### 五、流程控制与 NULL 处理

| 函数 | 说明 | 示例 |
| --- | --- | --- |
| `IF(expr, v1, v2)` | expr 为真返回 v1，否则 v2（MySQL 特有） | `if(salary > 8000, '高', '普通')` |

| `CASE WHEN ... THEN ... END` | 多分支条件 | 见下方示例 |

       case when salary >= 10000 then 'A'
            when salary >= 6000  then 'B'

       ifnull(commission, 0) as commission_real

-- 除零保护：b 为 0 时结果为 NULL，而不是报错

### 七、高频踩坑清单

- **`CONCAT` 遇 NULL 全变 NULL**：`concat(first_name, last_name)` 只要有一列是 NULL，整行结果就是 NULL。用 `concat_ws` 或 `ifnull(col, '')` 兜底。
- **`LENGTH` 数的是字节**：utf8mb4 下一个汉字 3 字节、emoji 4 字节，要数「字数」必须用 `char_length`。
- **`FORMAT` 返回字符串**：拿它 `order by` 会按字典序排（`'9' > '10'`），别用于数值计算和排序。
- **`GROUP_CONCAT` 会静默截断**：默认上限 `group_concat_max_len = 1024` 字节，超长直接丢数据且不报错，需要 `SET SESSION group_concat_max_len = 102400;`。
- **`NOW()` 与 `SYSDATE()` 不同**：`NOW()` 是语句开始时刻，同一条 SQL 里处处相同；`SYSDATE()` 是执行到该行的实时时刻，在基于语句的 binlog 复制下可能造成主从不一致，一般别用。
- **不要在索引列上套函数**：`where date_format(create_time, '%Y-%m') = '2026-11'` 索引直接失效，改写成范围条件（见「where 子句 → 索引相关」）。
- **`ORDER BY RAND()` 大表禁用**：全表扫描 + 排序 + 临时表，数据量上来直接打满 CPU。
- **除零**：`SELECT a/0` 返回 NULL 并给 warning，但 `INSERT`/`UPDATE` 在严格模式下会直接报 `Division by 0`；稳妥写法是 `a / nullif(b, 0)`。

### 八、综合示例

```sql
-- 按部门统计（where 过滤行，having 过滤分组）
select
  dept_id,
  count(*)                                  as emp_cnt,
  ifnull(sum(salary), 0)                    as salary_sum,
  round(avg(salary), 2)                     as salary_avg,
  max(salary)                               as salary_max,
  group_concat(name order by salary desc separator ',') as names
from emp
where status = 1
group by dept_id
having count(*) >= 2
order by salary_avg desc
limit 10;
```

**dev / prod 提示**：dev 端保持 `ONLY_FULL_GROUP_BY` 开启，能第一时间暴露不合规的分组查询；prod 端对大表聚合先用 `EXPLAIN` 看是否出现 `Using temporary`、`Using filesort`，必要时加覆盖索引或维护汇总表，别让实时 `count(*)` 扫全表。


### 字符串相关函数

> 前面「二、字符串函数」是速查表，这里按用途分组展开，补充返回值、边界行为、别名和易错点。

#### 1. 字符集与长度

| 函数 | 说明 | 示例（utf8mb4） |
| --- | --- | --- |
| `CHARSET(s)` | 返回字符串的字符集 | `charset('张三')` → `utf8mb4` |
| `COLLATION(s)` | 返回字符串的校对规则 | `collation('abc')` → `utf8mb4_0900_ai_ci` |
| `LENGTH(s)` / `OCTET_LENGTH(s)` | **字节**数 | `length('张三')` → 6 |
| `CHAR_LENGTH(s)` / `CHARACTER_LENGTH(s)` | **字符**数 | `char_length('张三')` → 2 |
| `BIT_LENGTH(s)` | 比特数，等于 `LENGTH(s) * 8` | `bit_length('A')` → 8 |

- 中文 3 字节、emoji 4 字节，凡是要「数几个字」一律用 `char_length`；`varchar(N)` 里的 N 也是**字符数**。
- 对 `BINARY` / `VARBINARY` / `BLOB`，`charset()` 返回 `binary`，此时 `length` 和 `char_length` 相等。
- 所有长度函数遇到 `NULL` 都返回 `NULL`，不是 0。

#### 2. 拼接

| 函数 | 说明 | 示例 |
| --- | --- | --- |
| `CONCAT(s1, s2, ...)` | 直接拼接，**任一参数为 NULL 则结果为 NULL** | `concat('a', null, 'b')` → `NULL` |
| `CONCAT_WS(sep, s1, s2, ...)` | 用 sep 分隔，自动跳过 NULL | `concat_ws('-', 'a', null, 'b')` → `a-b` |
| `REPEAT(s, n)` | 重复 n 次，n ≤ 0 返回空串 | `repeat('ab', 3)` → `ababab` |
| `SPACE(n)` | 生成 n 个空格 | `space(3)` |

- 数字参数会自动转字符串，`concat('No.', 1)` → `No.1`，不需要手动 `cast`。
- `CONCAT_WS` 的**分隔符若为 NULL，整个结果就是 NULL**；它跳过 NULL 值，但不会跳过空字符串 `''`，因此可能出现连续分隔符。
- `GROUP_CONCAT` 属于聚合函数（见「一、聚合函数」），是把**多行**拼成一行，和这里的**多列**拼接不是一回事。

#### 3. 大小写转换

| 函数 | 说明 |
| --- | --- |
| `UPPER(s)` / `UCASE(s)` | 转大写，两者是同义词 |
| `LOWER(s)` / `LCASE(s)` | 转小写，两者是同义词 |

- 对中文、数字无效果。
- **对二进制串（`BINARY`/`BLOB`）不生效**，需要先转字符集：`upper(convert(bin_col using utf8mb4))`。
- 大小写比较是否敏感由 `collation` 决定：`utf8mb4_0900_ai_ci` 是大小写不敏感（ci），`utf8mb4_bin` / `_as_cs` 才区分。

#### 4. 截取与定位

| 函数 | 说明 | 示例 |
| --- | --- | --- |
| `LEFT(s, n)` / `RIGHT(s, n)` | 从左 / 右取 n 个字符 | `left('abcdef', 3)` → `abc` |
| `SUBSTRING(s, pos, len)` | 从 pos 取 len 个字符，省略 len 则取到结尾 | `substring('abcdef', 2, 3)` → `bcd` |
| `SUBSTR` / `MID` | `SUBSTRING` 的同义词 | `mid('abcdef', 2, 3)` → `bcd` |
| `SUBSTRING_INDEX(s, delim, n)` | 按分隔符取前 n 段；n 为负则从右往左数 | `substring_index('a.b.c', '.', -1)` → `c` |
| `INSTR(s, sub)` | sub 在 s 中首次出现的位置，找不到返回 0 | `instr('abcdef', 'cd')` → 3 |
| `LOCATE(sub, s, pos)` | 同上，可指定起始位置 | `locate('cd', 'abcdef')` → 3 |
| `POSITION(sub IN s)` | 标准 SQL 写法，等价于 `LOCATE` | `position('cd' in 'abcdef')` → 3 |
| `FIND_IN_SET(s, 'a,b,c')` | 在逗号分隔列表中找序号，找不到返回 0 | `find_in_set('b', 'a,b,c')` → 2 |

**边界行为（很容易记错）**

- **位置一律从 1 开始，不是 0**：`substring(s, 0, 3)` 返回空串。
- `pos` 可以为负数，表示倒数第几位开始：`substring('abcdef', -3, 2)` → `de`。
- **`INSTR(s, sub)` 与 `LOCATE(sub, s)` 的参数顺序是反的**，这是最高频的踩坑点，建议固定只用一种。
- `INSTR` / `LOCATE` 找不到返回 **0**（不是 NULL、不是 -1），所以可以直接写 `where instr(name, '李') > 0`。
- `FIND_IN_SET` 要求列表是**逗号分隔的纯字符串**，元素里不能含逗号；用它查「标签」字段属于反范式设计，既用不上索引也不好维护，应拆关联表。

#### 5. 填充、替换与清理

| 函数 | 说明 | 示例 |
| --- | --- | --- |
| `LPAD(s, n, pad)` / `RPAD(s, n, pad)` | 左 / 右补齐到 n 个字符 | `lpad('7', 3, '0')` → `007` |
| `TRIM(s)` | 去掉首尾空格 | `trim('  a  ')` → `a` |
| `LTRIM(s)` / `RTRIM(s)` | 只去左 / 右空格 | |
| `REPLACE(s, from, to)` | 全局替换 | `replace('a-b-c', '-', '')` → `abc` |
| `INSERT(s, pos, len, new)` | 从 pos 起替换 len 个字符 | `insert('abcdef', 2, 3, 'X')` → `aXef` |
| `REVERSE(s)` | 反转 | `reverse('abc')` → `cba` |

- **`LPAD` / `RPAD` 在 n 小于原长度时会截断**：`lpad('abcdef', 3, '0')` → `abc`，补零场景要先确认长度。
- `TRIM` 完整语法是 `TRIM(BOTH 'x' FROM s)`，也支持 `LEADING` / `TRAILING`：`trim(both 'x' from 'xxabcxx')` → `abc`。默认只去**空格**，不去 tab、换行、全角空格，需要显式指定或用 `replace` 嵌套。
- `REPLACE` 大小写是否敏感取决于列的 `collation`；ci 规则下 `replace('ABC', 'a', '_')` 也会命中。
- **`INSERT()` 是字符串函数，不是 SQL 的 `INSERT` 语句**，名字相同但完全不同的东西。

#### 6. 比较与自定义排序

| 函数 | 说明 | 示例 |
| --- | --- | --- |
| `STRCMP(s1, s2)` | 逐字符比较，返回 -1 / 0 / 1 | `strcmp('abc', 'abd')` → -1 |
| `FIELD(s, s1, s2, ...)` | 返回 s 在列表中的位置，找不到返回 0 | `field('b', 'a', 'b', 'c')` → 2 |
| `ELT(n, s1, s2, ...)` | 返回列表中第 n 个字符串 | `elt(2, 'a', 'b', 'c')` → `b` |
| `SOUNDEX(s)` | 返回发音编码，用于英文模糊匹配 | `soundex('Smith')` |

- `STRCMP` 的结果受 `collation` 影响，ci 规则下 `strcmp('A', 'a')` 返回 **0**，要区分大小写得用 `binary` 或 `_bin` 规则。
- `FIELD` 最常见的用途是**自定义排序**：`order by field(status, 2, 1, 0)`，比一串 `case when` 简洁。
- 中文排序默认按字符编码，不保证是拼音序；要按拼音排需指定 `collation` 或转 GBK：`order by convert(name using gbk)`。

#### 7. 编码与格式化

| 函数 | 说明 |
| --- | --- |
| `FORMAT(x, d)` | 千分位格式化，**返回字符串**（不能参与数值排序） |
| `QUOTE(s)` | 加单引号并转义内部特殊字符，常用于拼动态 SQL |
| `ASCII(s)` | 返回首字符的 ASCII 码，`ascii('A')` → 65 |
| `CHAR(n, ...)` | 按字符集把数字转成字符，`char(65)` → `A` |
| `HEX(s)` / `UNHEX(s)` | 十六进制互转，排查乱码时很有用 |
| `CONV(n, from, to)` / `BIN(n)` / `OCT(n)` | 进制转换 |
| `TO_BASE64(s)` / `FROM_BASE64(s)` | Base64 编解码（5.6+） |
| `SHA2(s, n)` / `SHA1(s)` / `MD5(s)` | 摘要，n 可取 224/256/384/512 |

- 排查「看着一样但 `=` 不相等」的中文/隐藏字符问题，用 `hex(col)` 看原始字节最快。
- `QUOTE` 只做转义，**不等于参数绑定**；生产代码一律用预编译语句 `?` 占位，`QUOTE` 仅用于临时排查或 DBA 脚本。

#### 9. 实战写法

```sql
-- 手机号脱敏：138****8000
select concat(left(phone, 3), '****', right(phone, 4)) as phone_mask from user_demo;

-- 英文姓名首字母大写
select concat(upper(left(name, 1)), lower(substring(name, 2))) as name_fmt from emp;

-- 取邮箱域名并统计
select substring_index(email, '@', -1) as domain, count(*) as cnt
from emp group by domain order by cnt desc;

-- 按业务指定顺序排序（待审 2 在前，通过 1，驳回 0）
select id, status from emp order by field(status, 2, 1, 0), id;

-- 排查隐藏字符 / 乱码
select name, hex(name), length(name), char_length(name) from emp where name <> trim(name);
```

#### 10. 易错点速记

- `LENGTH` 数**字节**，`CHAR_LENGTH` 数**字符**。
- `CONCAT` 遇 NULL 全变 NULL，用 `CONCAT_WS` 或 `IFNULL(col, '')`。
- `INSTR(s, sub)` 与 `LOCATE(sub, s)` **参数顺序相反**。
- 位置从 **1** 开始，找不到返回 **0**。
- `LPAD/RPAD` 会**截断**超长原串。
- `FORMAT` 返回字符串，`ORDER BY` 会按字典序排。
- **在索引列上套任何函数（`left(phone,3)`、`upper(name)`、`trim(col)`）都会让索引失效**，要改成范围条件或建函数索引/生成列（见「where 子句 → 索引相关」）。
- 字符串函数对 `NULL` 输入基本都返回 `NULL`，聚合统计前先想清楚要不要 `IFNULL` 兜底。

### 数学相关函数

> 前面「三、数值函数」是速查表，这里按讲义清单逐个展开，补充返回值类型、边界行为和易错点。

#### 1. 讲义清单速查

| 函数 | 说明 | 示例 | 返回值 |
| --- | --- | --- | --- |
| `ABS(num)` | 绝对值 | `abs(-3.5)` | `3.5` |
| `BIN(n)` | 十进制转二进制字符串 | `bin(10)` | `1010` |
| `CEILING(n)` / `CEIL(n)` | 向上取整 | `ceiling(3.2)` | `4` |
| `CONV(n, from_base, to_base)` | 进制转换（2\~36 进制） | `conv('FF', 16, 10)` | `255` |
| `FLOOR(n)` | 向下取整 | `floor(3.8)` | `3` |
| `FORMAT(n, d)` | 保留 d 位小数并加千分位 | `format(1234567.5, 2)` | `1,234,567.50` |
| `HEX(n)` | 转十六进制 | `hex(255)` | `FF` |
| `LEAST(n1, n2, ...)` | 求一组值的最小值 | `least(3, 1, 2)` | `1` |
| `MOD(a, b)` | 取余 | `mod(10, 3)` | `1` |
| `RAND([seed])` | 随机数，范围含 0 不含 1.0 | `rand()` | `0.7153...` |

#### 2. 取整：CEILING / FLOOR / ROUND / TRUNCATE

- **讲义里「比 num2 大的最小整数」不够严谨**：应该是「**大于等于** n 的最小整数」。`ceiling(3)` 返回 `3` 而不是 `4`；同理 `floor(3)` 返回 `3`，是「**小于等于** n 的最大整数」。
- **负数方向最容易错**：取整是沿数轴方向，不是「远离零」。

| 表达式 | 结果 | 表达式 | 结果 |
| --- | --- | --- | --- |
| `ceiling(3.2)` | 4 | `floor(3.8)` | 3 |
| `ceiling(-3.2)` | **-3** | `floor(-3.8)` | **-4** |
| `round(3.5)` | 4 | `round(-3.5)` | -4 |

- `ROUND(x, d)` 四舍五入，`TRUNCATE(x, d)` 直接截断不进位；`ROUND` 对 `.5` 是「远离零」方向。
- `d` 可以为负数，表示对整数位取整：`round(1234, -2)` → `1200`。
- **除法 `/` 返回小数，整除要用 `DIV`**：`5 / 2` → `2.5000`，`5 div 2` → `2`。

#### 3. 取余：MOD

- `MOD(a, b)`、`a % b`、`a mod b` 三者等价。
- **除数为 0 返回 `NULL`**（`SELECT` 场景不报错，只给 warning），稳妥写法用 `nullif` 兜底。
- 负数取余的符号跟被除数：`mod(-5, 2)` → `-1`，`mod(5, -2)` → `1`。
- 常见用途：判奇偶 `mod(id, 2) = 1`、分表分片 `mod(user_id, 4)`、轮询取模。
- 浮点取余会按 DECIMAL 规则处理，可能有精度误差，尽量对整数用。

#### 4. 进制转换与位运算

| 函数 / 运算符 | 说明 | 示例 |
| --- | --- | --- |
| `BIN(n)` / `OCT(n)` / `HEX(n)` | 十进制转 2 / 8 / 16 进制字符串 | `oct(8)` → `10` |
| `CONV(n, from, to)` | 2\~36 进制互转，**返回字符串** | `conv('1010', 2, 16)` → `A` |
| `UNHEX(s)` | 十六进制串还原为二进制 | `unhex('4142')` → `AB` |
| `&` / \| / `^` / `~` | 按位与 / 或 / 异或 / 取反 | `5 & 3` → `1` |
| `<<` / `>>` | 左移 / 右移 | `1 << 3` → `8` |

- **`HEX` 对数字和对字符串语义完全不同**：`hex(255)` → `FF`（数值的十六进制），`hex('AB')` → `4142`（每个字符的字节编码）。排查乱码时用后者，做进制转换时用前者。
- `CONV` 的第一个参数可以写字符串，因此能处理超过 `BIGINT` 范围的大数；`bin(n)` 等价于 `conv(n, 10, 2)`。
- **`|` 在 SQL 里是按位或，不是「或者」** —— 之前笔记里 `select count(*)| count(列名)` 那种示意写法就是踩了这个坑，逻辑条件一律用 `OR`。
- 位运算常用于权限位存储（如 `permissions & 4` 判断是否有某权限），但可读性差、用不上索引，业务表建议改用关联表。

#### 5. 多值比较：LEAST / GREATEST

- `LEAST(n1, n2, ...)` 返回最小值，`GREATEST(n1, n2, ...)` 返回最大值，是**逐行标量函数**，不是聚合函数。
- **任一参数为 `NULL`，整个结果就是 `NULL`** —— 与聚合 `MIN`/`MAX`（跳过 NULL）行为相反，这是最高频的坑。用之前先 `IFNULL`：`least(ifnull(a, 0), ifnull(b, 0))`。
- 混合类型时按 MySQL 的类型提升规则比较，字符串和数字混用可能得出反直觉结果，先显式 `CAST`。
- 实用场景：把值夹在 0\~100 之间 `greatest(least(score, 100), 0)`；取两个时间中较晚的 `greatest(create_time, update_time)`。

#### 6. 随机数：RAND

- **范围含 0 但不含 1.0**（`0 <= v < 1.0`），讲义写的 `≤ 1.0` 不严谨，实际永远取不到 1.0。所以 `floor(rand() * 10)` 才能安全得到 0\~9。
- `RAND(seed)` 带相同种子会产生**同一串可复现序列**，适合造测试数据；不带种子每次不同。
- 取 `[m, n]` 闭区间随机整数：`floor(m + rand() * (n - m + 1))`。
- **`ORDER BY RAND()` 大表禁用**：全表扫描 + 全量排序 + 临时表，数据一上来就打满 CPU。随机抽样的替代方案：

```sql
-- 方案一：先随机定位主键，再顺序取（需主键近似连续）
select * from emp
where id >= (select floor(rand() * (select max(id) from emp)))
order by id limit 10;

-- 方案二：业务层先算出一批随机 id，再 where id in (...)
```

- 风险提示：`RAND()` 在**基于语句的 binlog 复制（statement）下不安全**，主从可能算出不同结果；prod 若必须用，改 row 格式或把随机值在应用层生成后写入。

#### 7. 格式化：FORMAT

- `FORMAT(x, d)` 返回的是**带千分位的字符串**，不是数字：`format(1234567.5, 2)` → `'1,234,567.50'`。
- 后果：拿它 `ORDER BY` 会按字典序排（`'9'` 排在 `'10'` 后面），参与算术会触发隐式转换，Java 侧 `Double.parseDouble` 遇到逗号直接抛异常。
- 只想保留小数位且结果仍为数值，用 `ROUND(x, d)` 或 `TRUNCATE(x, d)`；格式化展示应放在**应用层**做，别让数据库返回格式化字符串。

| `POW(x, y)` / `POWER(x, y)` | 幂运算 |
| `SQRT(x)` | 平方根，负数返回 `NULL` |
| `EXP(x)` / `LN(x)` / `LOG(x)` / `LOG10(x)` / `LOG2(x)` | 指数与对数 |

| `PI()` | 圆周率 |

#### 10. 易错点速记

- `CEILING` / `FLOOR` 对负数沿**数轴方向**取整，不是远离零；相等值时返回自身。
- `RAND()` 范围**不含 1.0**；`ORDER BY RAND()` 大表禁用。
- **`LEAST` / `GREATEST` 遇 NULL 返回 NULL**，与聚合 `MIN` / `MAX` 相反。
- **`HEX(数字)` 与 `HEX(字符串)` 语义不同**。
- `FORMAT` 返回字符串，不能用于数值排序和计算。
- `MOD(x, 0)` 返回 `NULL`；整除用 `DIV` 而不是 `/`。
- `|` 是按位或不是逻辑或；条件组合一律用 `OR`。
- **索引列上套数学函数会失效**（`where abs(amount) > 100`、`where mod(id, 2) = 1`），改写成范围条件或建生成列索引。
- 金额、精度敏感计算一律用 `DECIMAL`，不要对 `FLOAT` / `DOUBLE` 做 `ROUND`、`SUM` 后直接比较。

**dev / prod 提示**：dev 端保持严格模式，用 `SHOW WARNINGS` 抓 `MOD` 除零、`FORMAT` 隐式转换这类静默问题；prod 端避免在 `WHERE` / `ORDER BY` 里对索引列套数学函数，随机抽样改走主键范围，且确认 binlog 格式为 `ROW` 后再使用 `RAND()`。

> 前面「四、日期时间函数」是速查表，这里按讲义清单展开。截图最后一行把 `YEAR|Month|DATE` 和 `FROM_UNIXTIME()` 挤在一起且被截断，第 7 小节把时间戳部分补完整。

#### 1. 讲义清单速查

| 函数 | 说明 | 示例 |
| --- | --- | --- |
| `CURRENT_DATE()` | 当前日期 | `2026-11-07` |
| `CURRENT_TIME()` | 当前时间 | `14:30:00` |
| `CURRENT_TIMESTAMP()` | 当前时间戳（返回 DATETIME） | `2026-11-07 14:30:00` |
| `NOW()` | 当前日期时间 | `2026-11-07 14:30:00` |
| `DATE(datetime)` | 取 datetime 的日期部分 | `date(now())` → `2026-11-07` |
| `DATE_ADD(d, INTERVAL v unit)` | 在 d 上加一段时间 | `date_add(now(), interval 7 day)` |
| `DATE_SUB(d, INTERVAL v unit)` | 在 d 上减一段时间 | `date_sub(now(), interval 1 month)` |
| `DATEDIFF(d1, d2)` | 两个日期相差天数 | `datediff('2026-11-07', '2026-11-01')` → 6 |
| `TIMEDIFF(t1, t2)` | 两个时间差（时分秒） | `timediff('12:00:00', '09:30:00')` → `02:30:00` |
| `YEAR` / `MONTH` / `DAY(d)` | 取年 / 月 / 日 | `year(now())` → 2026 |
| `UNIX_TIMESTAMP()` | 当前时间的秒级时间戳 | 10 位整数 |
| `FROM_UNIXTIME(sec [, fmt])` | 秒级时间戳转日期（可指定格式） | `from_unixtime(sec, '%Y-%m-%d')` |

#### 2. 当前时间：NOW / CURRENT_* / SYSDATE

| 写法 | 等价形式 | 返回 |
| --- | --- | --- |
| `CURRENT_DATE` | `CURDATE()` | `2026-11-07` |
| `CURRENT_TIME` | `CURTIME()` | `14:30:00` |
| `CURRENT_TIMESTAMP` | `NOW()`、`LOCALTIME`、`LOCALTIMESTAMP` | `2026-11-07 14:30:00` |

- 这些关键字**带不带括号都可以**：`current_date` 和 `current_date()` 一样。
- `UTC_DATE()` / `UTC_TIME()` / `UTC_TIMESTAMP()` 返回 UTC 时间，跨时区业务优先用它们。
- **`NOW()` 是语句开始时刻**，同一条 SQL 里处处相同；`SYSDATE()` 是执行到该行的实时时刻。基于语句的 binlog 复制下 `SYSDATE()` 可能导致主从不一致，一般别用。
- 小数秒：`NOW(3)` 毫秒、`NOW(6)` 微秒（5.6.4+），但列也要定义成 `DATETIME(3)` / `DATETIME(6)` 才存得下。
- 写入 `TIMESTAMP` 列时，MySQL 会按会话 `time_zone` 把值转成 UTC 存储；`DATETIME` 则原样存字面值（见「日期时间类型要点」）。

#### 3. 提取与取值

| 函数 | 说明 |
| --- | --- |
| `DATE(d)` / `TIME(d)` | 取日期 / 时间部分 |
| `YEAR` / `MONTH` / `DAY(d)` | 年 / 月 / 日 |
| `HOUR` / `MINUTE` / `SECOND` / `MICROSECOND(d)` | 时 / 分 / 秒 / 微秒 |
| `DAYOFWEEK(d)` | 星期序号，**1 = 周日**，7 = 周六 |
| `WEEKDAY(d)` | 星期序号，**0 = 周一**，6 = 周日 |
| `DAYOFYEAR(d)` / `QUARTER(d)` / `WEEK(d)` | 年内第几天 / 季度 / 周数 |
| `DAYNAME(d)` / `MONTHNAME(d)` | 星期名 / 月份名，受 `lc_time_names` 影响 |
| `LAST_DAY(d)` | 当月最后一天 |
| `EXTRACT(unit FROM d)` | 标准 SQL 写法，如 `extract(year_month from now())` |

- **`DAYOFWEEK`（周日=1）和 `WEEKDAY`（周一=0）基准不同**，判断是否周末时别混用。
- `DATE('2026-11-07 14:30:00')` 得到 `'2026-11-07'`，常用来按天分组；但 `GROUP BY DATE(col)` 会让索引失效，大表建议加生成列或冗余一个 `stat_date` 字段。

#### 4. 日期加减：DATE_ADD / DATE_SUB

语法：`DATE_ADD(d, INTERVAL expr unit)`，`expr` 是数值或字符串，`unit` 是时间单位。

| 单位类型 | 可用值 |
| --- | --- |
| 日期 | `DAY`、`WEEK`、`MONTH`、`QUARTER`、`YEAR` |
| 时间 | `HOUR`、`MINUTE`、`SECOND`、`MICROSECOND` |
| 复合 | `YEAR_MONTH`、`DAY_HOUR`、`HOUR_MINUTE`、`MINUTE_SECOND`、`DAY_SECOND` 等 |

```sql
select date_add('2026-11-07', interval 7 day);        -- 2026-11-14
select date_sub(now(), interval 1 month);             -- 2026-10-07 ...
select date_add('2026-01-31', interval 1 month);     -- 2026-02-28（自动收敛到月末）
select date_add('2026-11-07 10:00:00', interval '1:30' hour_minute); -- 2026-11-07 11:30:00

-- 运算符简写（更常用）
select curdate() + interval 7 day, curdate() - interval 1 month;
```

- `ADDDATE` / `SUBDATE` 是同义词，`DATE_SUB(d, INTERVAL n unit)` 等价于 `DATE_ADD(d, INTERVAL -n unit)`。
- **加 `MONTH` / `YEAR` 会收敛到月末**：`2026-01-31 + 1 MONTH` 得到 `2026-02-28` 而不是 3 月 3 日，闰年同理。业务口径若是「固定 30 天」，必须明确写 `INTERVAL 30 DAY`，别用 `1 MONTH`。
- 复合单位的 `expr` 要写成带分隔符的字符串（`'1:30' HOUR_MINUTE`），写成数字会报错。

#### 5. 差值：DATEDIFF / TIMEDIFF / TIMESTAMPDIFF

| 函数 | 方向 | 说明 |
| --- | --- | --- |
| `DATEDIFF(d1, d2)` | **d1 - d2** | 只比较日期部分，**忽略时分秒**，返回整数天 |
| `TIMEDIFF(t1, t2)` | **t1 - t2** | 返回 `HH:MM:SS` 形式的 TIME 值 |
| `TIMESTAMPDIFF(unit, d1, d2)` | **d2 - d1** | 通用差值，unit 可到秒 / 月 / 年 |
| `PERIOD_DIFF(p1, p2)` | p1 - p2 | 比较 `YYYYMM` 格式的月份差 |

- **`DATEDIFF` 与 `TIMESTAMPDIFF` 的减法方向是反的**，这是本节最高频的坑：`datediff('2026-11-07','2026-11-01') = 6`，但 `timestampdiff(day, '2026-11-01','2026-11-07') = 6`。写之前先确认谁在前。
- `DATEDIFF` 忽略时分秒：`datediff('2026-11-07 00:00:00', '2026-11-06 23:59:59')` 结果是 **1**，不是 1 秒。
- `TIMEDIFF` 的结果上限是 `838:59:59`（TIME 类型范围），算长间隔会溢出，改用 `TIMESTAMPDIFF(HOUR, ...)`。
- 算年龄用 `timestampdiff(year, birthday, curdate())`，**不要用 `datediff(...) / 365`**（闰年会偏）。

#### 6. 格式化与解析：DATE_FORMAT / STR_TO_DATE

| 格式符 | 含义 | 格式符 | 含义 |
| --- | --- | --- | --- |
| `%Y` / `%y` | 四位年 / 两位年 | `%m` / `%c` | 补零月 / 不补零月 |
| `%d` / `%e` | 补零日 / 不补零日 | `%H` / `%h` | 24 小时 / 12 小时 |
| `%i` | **分钟** | `%s` / `%S` | 秒 |
| `%f` | 微秒 | `%p` | AM / PM |
| `%M` / `%b` | **月份名** / 缩写 | `%W` / `%a` | 星期名 / 缩写 |
| `%j` | 年内第几天 | `%u` / `%U` | 周数 |

```sql
select date_format(now(), '%Y-%m-%d %H:%i:%s');          -- 2026-11-07 14:30:00
select str_to_date('2026/11/07', '%Y/%m/%d');            -- 2026-11-07
select str_to_date('07-11-2026 14:30', '%d-%m-%Y %H:%i');-- 2026-11-07 14:30:00
```

- **`%i` 是分钟，`%M` 是月份名，`%m` 是补零月份，`%H` 是 24 小时** —— 按其他语言 `strftime` 的习惯写成 `%M` 取分钟会得到 `November`，是最常见的格式化事故。
- `STR_TO_DATE` 的格式串必须与输入**完全匹配**，不匹配返回 `NULL`（不会报错），上线前务必用真实数据验一遍。
- `DATE_FORMAT` 返回**字符串**，不能用于日期比较和排序；日期比较请直接用日期类型或 `DATE(col)`。
- 标准格式 `'2026-11-07'` 可以直接写日期字面量，MySQL 会隐式转换，不必滥用 `STR_TO_DATE`。

#### 7. Unix 时间戳：UNIX_TIMESTAMP / FROM_UNIXTIME

讲义截图最后一行只露出 `FROM_UNIXTIME()`，缺了配套说明，这里补完整：

```sql
select unix_timestamp();                                     -- 当前秒数（10 位）
select unix_timestamp('2026-11-07 00:00:00');                -- 日期转秒数
select from_unixtime(unix_timestamp());                      -- 秒数转 DATETIME
select from_unixtime(unix_timestamp(), '%Y-%m-%d %H:%i:%s');-- 秒数直接格式化（讲义常见写法）
```

| 函数 | 说明 |
| --- | --- |
| `UNIX_TIMESTAMP()` / `UNIX_TIMESTAMP(d)` | 当前时间 / 指定时间转秒级时间戳 |
| `FROM_UNIXTIME(sec)` / `FROM_UNIXTIME(sec, fmt)` | 秒数转 DATETIME / 按格式转字符串 |
| `TIME_TO_SEC(t)` / `SEC_TO_TIME(n)` | 时间与秒数互转 |
| `CONVERT_TZ(dt, from_tz, to_tz)` | 时区转换，需先初始化 MySQL 时区表 |

- **秒级是 10 位，毫秒级是 13 位**：Java 的 `System.currentTimeMillis()` 直接喂给 `FROM_UNIXTIME` 会得到错误日期，要先除以 1000。
- `UNIX_TIMESTAMP` / `FROM_UNIXTIME` **受会话 `time_zone` 影响**，跨时区服务必须统一时区设置。
- `TIMESTAMP` 列有 2038 年上限（4 字节存秒数），`DATETIME` 能到 9999 年；即使函数本身能算更大范围，存储类型仍会卡住。
- 工程建议：业务表存 `DATETIME` 而不是 `INT` 时间戳，可读性更好、能直接用日期函数；需要跨时区再额外存时区或用 `TIMESTAMP`。

#### 9. 实战写法

```sql
-- 近 7 天（左闭右开，create_time 上的索引可用）
select * from orders
where create_time >= curdate() - interval 7 day
  and create_time <  curdate() + interval 1 day;

-- 本月：先算出月初，再找下月初，全部用范围条件
set @month_start = date_sub(curdate(), interval dayofmonth(curdate()) - 1 day);
select * from orders
where create_time >= @month_start
  and create_time <  date_add(@month_start, interval 1 month);

-- 年龄与本月生日
select name, timestampdiff(year, birthday, curdate()) as age from emp;
-- 注意：month(birthday) 用不上索引，大表应冗余一个 birthday_month 列
select * from emp where month(birthday) = month(curdate());

-- 按天统计（大表建议冗余一个 stat_date 生成列再分组）
select date(create_time) as day, count(*) as cnt from orders
where create_time >= curdate() - interval 30 day
group by date(create_time) order by day;
```

**反例（索引失效，别这么写）**：`where date(create_time) = curdate()`、`where year(create_time) = 2026` —— 都是对索引列套函数，应改成上面的左闭右开范围条件。

#### 10. 易错点速记

- `DATEDIFF(d1, d2)` 是 **d1 - d2**，`TIMESTAMPDIFF(unit, d1, d2)` 是 **d2 - d1**，方向相反。
- `DATEDIFF` 忽略时分秒；`TIMEDIFF` 上限 838 小时。
- `%i` 是分钟、`%M` 是月份名、`%m` 是补零月、`%H` 是 24 小时。
- `DAYOFWEEK` 周日=1，`WEEKDAY` 周一=0。
- `DATE_ADD(... INTERVAL 1 MONTH)` 会自动收敛到月末，不等于 30 天。
- `NOW()` 是语句开始时刻，`SYSDATE()` 是实时时刻，后者在 statement binlog 下不安全。
- `DATE_FORMAT` / `STR_TO_DATE` 返回字符串；格式不匹配返回 `NULL` 不报错。
- 毫秒时间戳 13 位，`FROM_UNIXTIME` 只认 10 位秒。
- **索引列上套任何日期函数都会失效**，一律改写成范围条件。
- `TIMESTAMP` 存 UTC 且有 2038 上限，`DATETIME` 存字面值到 9999 年；时区不统一会导致写入读出差 8 小时。

**dev / prod 提示**：dev 端显式 `SET time_zone = '+08:00'` 并固定测试数据日期，把格式化和时区转换各验一遍；prod 端建表统一 `DATETIME` + 明确时区约定，所有时间范围查询走左闭右开（避免在索引列上套函数），跨时区写入由应用层统一转 UTC，并确认 binlog 格式为 `ROW` 以规避 `SYSDATE()` 等不确定函数。


### 流程控制函数

> 前面「五、流程控制与 NULL 处理」是速查表，这里按讲义清单展开：把 `IF` / `IFNULL` / `CASE` 三个函数讲透，补齐同族的 `NULLIF` / `COALESCE` / `ISNULL`，并给出可直接运行的验证 SQL。截图里三条 `emp` 查询的写法问题在第 5 小节说明。

#### 1. 讲义清单速查

| 函数 | 讲义语义 | 规范表述 | 示例 |
| --- | --- | --- | --- |
| `IF(expr1, expr2, expr3)` | expr1 为 True 返回 expr2，否则 expr3 | expr1 **非零且非 NULL** 时返回 expr2，否则返回 expr3 | `if(comm is null, 0, comm)` |
| `IFNULL(expr1, expr2)` | expr1 不为 NULL 返回 expr1，否则返回 expr2 | 同左，只接受两个参数，MySQL 方言 | `ifnull(comm, 0)` |
| `CASE WHEN expr1 THEN expr2 WHEN expr3 THEN expr4 ELSE expr5 END` | 类似多重分支 | 自上而下判断，第一个为真的分支返回对应值，都不满足走 `ELSE` | 见第 4 小节 |

讲义右侧第三行的说明有个笔误：「如果 expr2 为…，返回 expr4」应为 **「如果 expr3 为 TRUE，则返回 expr4」** —— `CASE` 的每个 `WHEN` 后面都是一个独立的布尔表达式，不是接着上一个分支的返回值判断。

另外讲义里 `END;` 后面的分号只是 **SQL 语句的结束符**，而 `END` 是 `CASE` 语法本身的一部分，漏写 `END` 会直接报 1064 语法错误。

#### 2. IF(expr1, expr2, expr3)

- `expr1` 按**数值**判断真假：非 0 为真，0 为假，**NULL 视为假**。
- 传字符串会被隐式转成数字：`if('abc', 1, 2)` 返回 2（转 0），`if('2x', 1, 2)` 返回 1 但会给 `Truncated incorrect DOUBLE value` warning。条件就该写明确的比较表达式。
- `expr2` / `expr3` 可以是任意表达式（列、子查询、嵌套 `IF`）；嵌套超过两层可读性很差，换 `CASE`。

| expr1 | 返回 |
| --- | --- |
| `1`、`-1`、`0.5`、`'2'` | expr2（真） |
| `0`、`0.0`、`'abc'`、`''` | expr3（假） |
| `NULL`、`1 = NULL`（结果为 NULL） | expr3（NULL 视为假） |

- **返回类型只有一个**：MySQL 会按所有分支推断统一类型。`if(flag, 1, 'N/A')` 会把数字转成字符串，JDBC 取出来可能是 `String` 而不是 `Integer`。分支类型尽量一致，语义不同时拆成两列。
- **别和存储过程的 `IF` 语句混了**：`IF()` 是标量函数，能出现在 `SELECT` / `WHERE` / `ORDER BY` 的任意表达式位置；`IF ... THEN ... END IF` 是流程控制语句，只能写在存储过程、函数、触发器里（见第 9 小节）。

#### 3. NULL 处理四兄弟：IFNULL / COALESCE / NULLIF / ISNULL

| 函数 | 语义 | 参数 | 可移植性 |
| --- | --- | --- | --- |
| `IFNULL(v1, v2)` | v1 为 NULL 返回 v2，否则返回 v1 | 2 个 | MySQL 方言 |
| `COALESCE(v1, v2, ...)` | 返回第一个非 NULL 值，全为 NULL 才返回 NULL | 任意多个 | **标准 SQL**，跨库首选 |
| `NULLIF(v1, v2)` | v1 与 v2 相等返回 NULL，否则返回 v1 | 2 个 | 标准 SQL |
| `ISNULL(v)` | v 为 NULL 返回 1，否则返回 0 | 1 个 | MySQL 方言，等价于 `v IS NULL` |

- `IFNULL(v1, v2)` 等价于 `COALESCE(v1, v2)`，也等价于 `CASE WHEN v1 IS NULL THEN v2 ELSE v1 END`。多级兜底用 `coalesce(mobile, phone, '无')`，比嵌套 `ifnull(ifnull(...))` 清爽。
- **`NULLIF` 常用来「造 NULL」**：`a / nullif(b, 0)` 避免除零（见「七、高频踩坑清单」）；`nullif(trim(col), '')` 把空串规范成 NULL。
- `NULLIF` 内部用的是 `=` 比较，所以 `NULLIF(NULL, NULL)` 返回 **NULL**（也就是 v1 本身，而不是 1/0）；要判断相等且兼容 NULL 得用 `<=>`（安全等于）。
- **只兜 NULL，不兜空串和 0**：`ifnull(comm, 0)` 遇到 `comm = ''` 会原样返回空串，参与算术时被转成 0 并可能产生 warning。数据不干净时用 `coalesce(nullif(comm, ''), 0)`。
- 返回类型同样由所有分支推断：`ifnull(int_col, '0')` 结果是**字符串**，拿去 `ORDER BY` 会按字典序排。

#### 4. CASE：两种写法与短路求值

**搜索 CASE**（讲义里的形式，条件可任意复杂，最常用）：

```sql
case
  when sal >= 10000 then 'A'
  when sal >= 6000  then 'B'
  when sal is null  then '未知'
  else 'C'
end as level
```

**简单 CASE**（只能做等值比较）：

```sql
case deptno
  when 10 then '研发'
  when 20 then '市场'
  else '其他'
end as dept_name

-- 等价于 case when deptno = 10 then ... when deptno = 20 then ... else ... end
```

| 要点 | 说明 |
| --- | --- |
| `END` 必须写 | 漏掉直接 1064 语法错误；`END` 后可跟 `as 别名` |
| `ELSE` 可省略 | 省略且不命中任何分支时返回 **NULL**，统计时容易漏数，建议显式写 `ELSE 0` / `ELSE '其他'` |
| 短路求值 | 自上而下，**命中第一个为真的分支就返回**，后续分支不再计算；区间判断必须按大小顺序排好 |
| NULL 判断 | `WHEN col = NULL` 永不命中（结果是 UNKNOWN），必须写 `WHEN col IS NULL` |
| 简单 CASE 的 NULL | `CASE NULL WHEN NULL THEN ...` 也不命中，因为它用的是 `=`；列可能为 NULL 时一律用搜索 CASE |
| 分支类型 | 所有 `THEN` / `ELSE` 返回值类型会被统一，混用数字和字符串会发生隐式转换 |
| 可用位置 | `SELECT`、`WHERE`、`ORDER BY`、`GROUP BY`、`HAVING`、聚合函数内部、`UPDATE SET` 都能用 |

> 短路求值的实用价值：把代价高或可能报错的分支放后面，例如 `case when cnt > 0 then total / cnt else 0 end`，`cnt = 0` 时根本不会走到除法。

#### 5. 讲义的三条 emp 查询：等价性与正确写法

三条语句解决的是同一个问题：**`sal + comm` 里 `comm` 为 NULL 时整个结果变 NULL**（NULL 参与任何算术运算结果都是 NULL，不是 0）。所以必须先兜底再相加。

```sql
-- ① 讲义写法：IF + IS NULL（正确）
select ename, sal + if(comm is null, 0, comm) as total from emp;

-- ② 讲义写法：IFNULL（最简洁，推荐）
select ename, sal + ifnull(comm, 0) as total from emp;

-- ③ 讲义写法（注意多了内层 select）
select sal + (select case when comm is null then 0 else comm end), ename from emp;
-- 规范写法：CASE ... END 本身就是标量表达式，不需要再套 select
select ename, sal + (case when comm is null then 0 else comm end) as total from emp;

-- ④ 跨库可移植写法
select ename, sal + coalesce(comm, 0) as total from emp;
```

- ① ② ④ 完全等价；② 最短，④ 可移植到 PostgreSQL / Oracle / SQL Server。
- ③ 里 `CASE` 前面多写了一层 `select`，使它变成**标量子查询**（无 `FROM`、引用外层 `comm` 的相关子查询）。MySQL 多数版本能解析，但纯属多余，在其他数据库、部分 ORM 的 SQL 解析器中可能直接报错，规范写法是让 `CASE ... END` 直接做表达式。
- **`comm is null` 不能写成 `comm = null`**：后者结果是 UNKNOWN，条件永远不命中，① 会退化成 `sal + comm` 全部返回 NULL。这是本章最容易静默出错的一处，与「where 子句 → NULL 三值逻辑」是同一条规则。
- 两列都可能为 NULL 时更直白：`ifnull(sal, 0) + ifnull(comm, 0)`。

最小可运行验证：

```sql
create table emp (
  empno int primary key auto_increment,
  ename varchar(20) not null,
  sal   decimal(10, 2),
  comm  decimal(10, 2) default null
) default charset = utf8mb4;

insert into emp(ename, sal, comm) values
  ('SMITH', 800,  NULL),
  ('ALLEN', 1600, 300),
  ('WARD',  1250, 500),
  ('JONES', 2975, NULL);

-- 对照：直接相加 vs 兜底后相加
select ename, sal, comm,
       sal + comm                        as raw_total,  -- comm 为 NULL 的两行结果是 NULL
       sal + ifnull(comm, 0)            as total,      -- 800 / 1900 / 1750 / 2975
       if(comm is null, '无奖金', '有奖金') as comm_flag
from emp;
```

#### 6. 验证 SQL（可直接贴进客户端）

```sql
select
  if(1 > 0, 'yes', 'no')                          as c1,   -- yes
  if(null, 'yes', 'no')                           as c2,   -- no（NULL 视为假）
  if(0, 'yes', 'no')                              as c3,   -- no
  if(-1, 'yes', 'no')                             as c4,   -- yes
  ifnull(null, 'fallback')                        as c5,   -- fallback
  coalesce(null, null, 'third')                   as c6,   -- third
  nullif(5, 5)                                    as c7,   -- NULL
  nullif(5, 6)                                    as c8,   -- 5
  isnull(null)                                    as c9,   -- 1
  null <=> null                                   as c10,  -- 1
  null = null                                     as c11,  -- NULL
  case when 1 = 1 then 'A' else 'B' end           as c12,  -- A
  case when 1 = null then 'A' else 'B' end        as c13,  -- B
  case null when null then 'A' else 'B' end       as c14,  -- B（简单 CASE 的 NULL 不命中）
  case when 2 > 1 then 'A' when 1 = 1 then 'B' else 'C' end as c15, -- A（短路）
  case 3 when 1 then 'one' when 2 then 'two' end  as c16,  -- NULL（无 ELSE 且不命中）
  100 + null                                      as c17;  -- NULL
```

#### 7. 实战：条件聚合、行转列与自定义排序

**条件聚合（行转列）** —— 面试和业务报表都高频：

```sql
select
  deptno,
  count(*)                                             as emp_cnt,
  sum(case when job = 'MANAGER' then sal else 0 end)  as manager_sal,
  count(case when comm is not null then 1 end)         as has_comm_cnt,
  sum(case when sal >= 3000 then 1 else 0 end)         as high_sal_cnt
from emp
group by deptno;
```

> **`COUNT(CASE WHEN ... THEN 1 END)` 的 `ELSE` 必须省略**（或写 `ELSE NULL`）。写成 `ELSE 0` 时每行都会被计数 —— `COUNT` 只跳过 NULL，结果恒等于 `count(*)`，这是本节最经典的错。
> `SUM` 反过来：`sum(case when ... then 1 else 0 end)` 用 `ELSE 0` 才对；若省略 `ELSE` 且分组内全不命中，`SUM` 返回 NULL 而不是 0，展示前要再套 `ifnull(..., 0)`。

**`AVG` 与 `IFNULL` 的坑**：

```sql
-- SUM 会跳过 NULL，两种写法结果一样
select sum(comm) as s1, sum(ifnull(comm, 0)) as s2 from emp;
-- AVG 的分母是「非 NULL 行数」，先填 0 会把 NULL 当 0 计入分母，均值被拉低
select avg(comm) as avg_comm, avg(ifnull(comm, 0)) as avg_with_zero from emp;
-- 空集或全 NULL 时聚合返回 NULL，展示层要 0 就在外层兜底
select ifnull(sum(comm), 0) as s from emp where 1 = 0;
```

**自定义排序**（呼应「字符串相关函数」里的 `FIELD`）：

```sql
select ename, job, sal from emp
order by case job
           when 'PRESIDENT' then 1
           when 'MANAGER'   then 2
           when 'ANALYST'   then 3
           else 4 end,
         sal desc;
-- FIELD 简写要注意：未命中时返回 0，会排在最前，需额外加一个排序键处理
```

**批量更新**：

```sql
update emp
set sal = case
            when deptno = 10 then sal * 1.10
            when deptno = 20 then sal * 1.05
            else sal
          end
where deptno in (10, 20);
```

> 必须带 `WHERE`：不带的话虽然 `ELSE sal` 值不变，但会全表加写锁、产生大量 binlog 和触发器副作用。上线前先 `START TRANSACTION` 跑一遍并核对影响行数，确认后再 `COMMIT`。

#### 8. 在 WHERE / ORDER BY 里用，以及索引代价

| 反例（索引失效 / filesort） | 正例 |
| --- | --- |
| `where ifnull(comm, 0) > 0` | `where comm > 0`（NULL 天然不满足，语义一致） |
| `where if(status = 1, create_time, update_time) > '2026-01-01'` | 拆成两个 `AND ... OR ...` 范围条件，或冗余一个 `sort_time` 列并建索引 |
| `where case when vip = 1 then 'A' else 'B' end = 'A'` | `where vip = 1` |
| `order by case job when 'MANAGER' then 1 else 2 end` | 要排序走索引就冗余一个 `job_rank` 列 |

- **`IFNULL(comm, 0) > 0` 与 `comm > 0` 为什么等价**：`comm IS NULL` 时前者算出 0 不满足，后者结果是 UNKNOWN 同样不返回。凡是「给 NULL 兜默认值再比较」，基本都能直接改成裸列比较。
- `WHERE` 里一旦对索引列套了任何函数（包括 `IF` / `CASE` / `IFNULL`），B+ 树就用不上了，退化为全表扫描（见「where 子句 → 索引相关」）。
- `ORDER BY` 里用 `CASE` / `FIELD` 必然产生 `Using filesort`；小结果集无所谓，大表分页要改成排序列或冗余排名字段。
- 反过来，**`SELECT` 列表和 `GROUP BY` 之后用这些函数不影响索引过滤**，代价主要是 CPU 和临时表，可以放心用。

#### 9. 易混：流程控制「语句」不是「函数」

讲义标题的「流程控制函数」指能嵌进 SQL 表达式的标量函数。MySQL 另有一套**流程控制语句**，只能写在存储过程 / 存储函数 / 触发器 / 事件里：

| 语句 | 语法骨架 | 对应编程概念 |
| --- | --- | --- |
| `IF` 语句 | `IF cond THEN ... ELSEIF cond THEN ... ELSE ... END IF;` | if / else |
| `CASE` 语句 | `CASE val WHEN ... THEN ... ELSE ... END CASE;` | switch |
| `LOOP` | `label: LOOP ... LEAVE label; END LOOP label;` | while(true) + break |
| `WHILE` | `WHILE cond DO ... END WHILE;` | while |
| `REPEAT` | `REPEAT ... UNTIL cond END REPEAT;` | do...while |
| `LEAVE` / `ITERATE` | `LEAVE label;` / `ITERATE label;` | break / continue |

```sql
delimiter $$
create procedure give_bonus(in p_empno int, inout p_msg varchar(100))
begin
  declare v_sal decimal(10, 2);

  select sal into v_sal from emp where empno = p_empno;

  -- 这里是 IF 语句，结尾是 END IF，不是 IF() 函数
  if v_sal is null then
    set p_msg = '员工不存在';
  elseif v_sal < 2000 then
    update emp set comm = ifnull(comm, 0) + 500 where empno = p_empno;  -- 这里是 IFNULL() 函数
    set p_msg = '已发放 500';
  else
    set p_msg = '薪资达标，不发放';
  end if;
end$$
delimiter ;

call give_bonus(1, @msg);
select @msg;
```

一句话区分：**`IF(cond, a, b)` 返回一个值，`IF ... THEN ... END IF` 执行一段语句块**。面试被问「MySQL 的流程控制」时先确认问的是哪一类。

#### 10. 易错点速记与工程建议

- `IF` 的条件按数值判真假，**NULL 和 0 都算假**；字符串条件会被隐式转数字。
- `IFNULL` / `COALESCE` 只兜 NULL，不兜空串；数据不干净用 `coalesce(nullif(col, ''), 0)`。
- `CASE` 必须有 `END`，`ELSE` 省略时返回 NULL；多个 `WHEN` 短路，区间顺序别写反。
- `WHEN col = NULL` 永不命中，一律用 `IS NULL`；简单 CASE 同样处理不了 NULL。
- `COUNT(CASE WHEN ... THEN 1 ELSE 0 END)` 恒等于 `count(*)`，`ELSE` 要省略。
- `AVG(IFNULL(col, 0))` 会把 NULL 当 0 拉低均值，`SUM` 则不受影响。
- 讲义第三条 emp 查询里 `CASE` 前多余的 `select` 应删掉，`CASE ... END` 本身就是表达式。
- 所有 `THEN` / `ELSE` 尽量保持同一类型，避免隐式转换让 JDBC 侧拿到 `String`、或让排序按字典序。
- `IF` / `IFNULL` 是 MySQL 方言，要跨库就用标准 SQL 的 `CASE WHEN` 和 `COALESCE`。
- **索引列上套 `IF` / `CASE` / `IFNULL` 同样会失效**，`WHERE` 里优先改写成裸列条件。

**dev / prod 提示**：dev 端保持严格模式，用 `SHOW WARNINGS` 抓 `IF('2x', ...)`、`IFNULL(int_col, '0')` 这类隐式转换；给 `comm` 造 NULL / 0 / 空串三种数据，把「直接相加」和「兜底后相加」各跑一遍。prod 端把 `IFNULL(col, 0) > 0` 一类条件改回裸列比较以保住索引，大表条件聚合先看 `EXPLAIN` 是否出现 `Using temporary` / `Using filesort`；多分支业务规则（等级、费率）优先放字典表或应用层配置，别硬编码在几十处 SQL 的 `CASE` 里；`UPDATE ... SET CASE` 必须先用 `WHERE` 限定范围并在事务里核对影响行数。


## 多表查询

> 前面所有查询都是单表，而真实业务数据按范式拆在多张表里。本节从「连接的本质」讲到七种连接写法，重点展开**自连接**（员工-经理、分类树、找重复、相邻行比较），最后给一份可整段执行的验证脚本和性能要点。所有示例共用同一份 `dept` / `emp` 数据（见第 8 小节）。

### 1. 连接的本质：笛卡尔积 + 过滤

多表查询在逻辑上只有两步：

1. **做笛卡尔积**：左表 m 行、右表 n 行，先拼出 m × n 行的临时结果，每行包含两表所有列。
2. **按条件过滤**：`ON` / `WHERE` 把不满足连接条件的行筛掉。

```sql
-- 6 行 emp × 4 行 dept = 24 行，这就是笛卡尔积
select e.ename, d.dname from emp e, dept d;

-- 加上连接条件，24 行筛成 5 行
select e.ename, d.dname from emp e, dept d where e.deptno = d.deptno;
```

- **漏写连接条件就是灾难**：两张 10 万行的表直接炸出 100 亿行中间结果，轻则查询卡死，重则写满临时表空间。看到慢查询的 `rows` 异常大，先检查是不是漏了 `ON`。
- 表别名不是可选项：`from emp e join dept d on e.deptno = d.deptno`，后面所有列都用 `别名.列名` 限定，避免同名列歧义（`deptno` 两张表都有）。
- 一旦给表起了别名，本语句内就必须用别名，再写原表名会报 `Unknown column`。

### 2. 连接类型总览

| 写法 | 名称 | 保留哪些行 | MySQL 支持情况 |
| --- | --- | --- | --- |
| `a, b` 或 `a cross join b` | 交叉连接 | 两表全部组合，m × n 行 | 支持 |
| `a inner join b on ...` | 内连接 | 只保留匹配成功的行 | 支持，`inner` 可省略 |
| `a left [outer] join b on ...` | 左外连接 | 左表全部 + 右表匹配，不匹配补 NULL | 支持 |
| `a right [outer] join b on ...` | 右外连接 | 右表全部 + 左表匹配 | 支持，可改写成左连接 |
| `a full outer join b on ...` | 全外连接 | 两表全部 | **不支持**，用 `union` 模拟 |
| `a natural join b` | 自然连接 | 按所有同名列自动等值连接 | 支持，**生产禁用** |
| `a join b using (col)` | 同名列连接 | 同内连接，输出列合并为一列 | 支持 |
| `a join a2 on ...` | 自连接 | 用法而非语法：同一张表起两个别名 | 支持 |

- 连接类型只决定**保留哪些行**，不决定性能；性能看的是连接列有没有索引、驱动表选得对不对（见第 9 小节）。
- 外连接用 `left` 还是 `right` 只取决于「哪张表要全部保留」，把表顺序调换一下就能互相改写。

### 3. 交叉连接 CROSS JOIN

```sql
-- 24 行：每个员工和每个部门各组合一次
select e.ename, d.dname from emp e cross join dept d;

-- 等价写法（逗号连接，不推荐，容易漏条件）
select e.ename, d.dname from emp e, dept d;
```

- 交叉连接本身几乎不用来查业务数据，但**给报表补零**很好用：4 个部门 × 3 个月，先拼出完整骨架再左连接真实数据。

```sql
-- 维表全组合：保证每个月每个部门都有一行，没有数据的显示 0（假设有 sale(deptno, dt, amt) 明细表）
select d.dname, m.mon, ifnull(t.amt, 0) as amt
from dept d
cross join (select 1 as mon union all select 2 union all select 3) m
left join (select deptno, month(dt) as mon, sum(amt) as amt
           from sale group by deptno, month(dt)) t
  on t.deptno = d.deptno and t.mon = m.mon
order by d.deptno, m.mon;
```

- MySQL 里 `JOIN` / `CROSS JOIN` / `INNER JOIN` **语法等价**，所以 `cross join ... on ...` 也能跑；但标准 SQL 里 `CROSS JOIN` 不接受 `ON`，跨库时别这么写。

### 4. 内连接 INNER JOIN

```sql
-- 显式连接（推荐）：连接条件放 on，业务过滤放 where
select e.ename, e.sal, d.dname
from emp e
join dept d on e.deptno = d.deptno
where e.sal > 6000;

-- 隐式连接（逗号 + where）：结果一样，但条件和过滤混在一起，表一多就难维护
select e.ename, d.dname from emp e, dept d where e.deptno = d.deptno;
```

- 内连接 `ON` 里写附加过滤条件和写在 `WHERE` 里**结果等价**（都会筛掉不匹配的行），区别只在可读性；但外连接里两者完全不同，见第 5 小节。
- `ON` 条件数量：n 张表连接至少 n - 1 个连接条件，少一个就多一层笛卡尔积。
- `USING` 与 `ON` 的差别：

```sql
-- on：两表都有 deptno 列，select * 会输出两列 deptno
select * from emp e join dept d on e.deptno = d.deptno;

-- using：同名列只输出一次，且排在最前
select * from emp e join dept d using (deptno);
```

- 三表连接（员工 + 上级 + 部门），每个连接条件都要写全：

```sql
select e.ename as emp_name, m.ename as mgr_name, d.dname
from emp e
join emp m  on e.mgr = m.empno
join dept d on e.deptno = d.deptno;
```

- **`NATURAL JOIN` 别用**：它按两表所有同名列自动等值连接，哪天给两张表都加了 `create_time`，连接条件就悄悄变了，排查起来极痛苦。`USING` 至少把参与连接的列写明了。

### 5. 外连接 LEFT / RIGHT JOIN

外连接 = 内连接的结果 + **保留表中没匹配上的行**（另一侧所有列补 NULL）。

#### 5.1 基本用法与左右互换

```sql
-- 左连接：保留 emp 全部 6 行，周八没有部门，dname 为 NULL
select e.ename, d.dname
from emp e left join dept d on e.deptno = d.deptno;

-- 等价改写：调换表顺序 + 改 right
select e.ename, d.dname
from dept d right join emp e on e.deptno = d.deptno;
```

`a left join b` **不等于** `b left join a`，但**等价于** `b right join a`。

#### 5.2 ON 里的条件和 WHERE 里的条件，结果完全不同

这是外连接第一大坑，看两组对比：

```sql
-- A：附加条件写在 ON 里 —— 左表仍然全保留，非市场部的行 dname 为 NULL
select e.ename, d.dname
from emp e left join dept d
  on d.deptno = e.deptno and d.dname = '市场';

-- B：附加条件写在 WHERE 里 —— 退化成内连接，只剩市场部的 2 行
select e.ename, d.dname
from emp e left join dept d on d.deptno = e.deptno
where d.dname = '市场';
```

| 条件位置 | 语义 | 结果 |
| --- | --- | --- |
| `ON ... and 右表条件` | 只影响「能不能连上」，连不上就补 NULL | 左表行数不变 |
| `WHERE 右表条件` | 对连接后的结果再过滤 | 右表为 NULL 的行被筛掉，等价内连接 |

> 记住一句：**想让左表全部保留，右表的过滤条件必须放 `ON`；放到 `WHERE` 里就等于自己把外连接写成了内连接。**

#### 5.3 反连接：找「没有匹配」的行

```sql
-- 没有员工的部门（只有 40 号新部门）
select d.deptno, d.dname
from dept d left join emp e on e.deptno = d.deptno
where e.empno is null;

-- 没有部门的员工（只有周八）
select e.empno, e.ename
from emp e left join dept d on e.deptno = d.deptno
where d.deptno is null;
```

- 判断条件要用**右表的主键或非空列** `IS NULL`，用可能本身为 NULL 的列会误判。
- 反连接也可以用 `NOT EXISTS`；**别用 `NOT IN`**，子查询结果一旦含 NULL，整个条件变 UNKNOWN，直接返回空集（呼应「where 子句 → 易错点」）。

#### 5.4 全外连接：MySQL 用 UNION 模拟

```sql
select e.ename, d.dname from emp e left join dept d on e.deptno = d.deptno
union
select e.ename, d.dname from emp e right join dept d on e.deptno = d.deptno;
```

`union` 会去重，两边都匹配上的行只出现一次，正好等价于 `FULL OUTER JOIN`；用 `union all` 会出重复行。

#### 5.5 左连接 + 聚合：`count(*)` 会骗你

```sql
select d.deptno, d.dname,
       count(*)           as cnt_star,   -- 40 号部门是 1，不是 0
       count(e.empno)     as cnt_emp,    -- 40 号部门是 0，正确
       ifnull(sum(e.sal), 0) as sal_sum
from dept d left join emp e on e.deptno = d.deptno
group by d.deptno, d.dname;
```

`dept 40` 没有员工，但左连接仍会为它产生一行（右表列全 NULL），`count(*)` 把这行也算上，于是得到 1。**统计左表行数要用 `count(左表主键)`，或者干脆用 `count(distinct 左表主键)`。**

#### 5.6 多表外连接：三张表怎么连

```sql
-- dept 是主表，左连接 emp，再左连接每个员工的绩效记录
select d.dname, e.ename, p.level
from dept d
left join emp  e on e.deptno = d.deptno
left join perf p on p.empno  = e.empno;
```

- 每个 `left join` 的 `ON` **只管自己那一对表**，别把三张表的条件塞进一个大 `ON`，否则语义不清且容易漏行。
- 链条方向要一致：`a left join b on ... left join c on b.x = c.x`，`c` 的 `ON` 引用 `b` 的列；如果写成 `on a.x = c.x` 就把 `c` 和主表直接绑上，`b` 为空时 `c` 也连不出来。
- **从表之间一对多会放大行数**：`dept` 1 行、`emp` 3 行、每人 5 条绩效，结果就是 15 行，`sum(主表字段)` 会翻 5 倍。要统计得先聚合子表。

#### 5.7 只取右表「最新一条」：避免一对多放大

这是外连接最实战的模板：主表左连接从表，但只需要从表里最新的一条。

```sql
-- perf 结构：perf(id, empno, level, ym)

-- 写法 A：join 聚合后的 id（推荐，两次扫描，不相关子查询）
select e.ename, p.level, p.ym
from emp e
left join (select empno, max(id) as max_id from perf group by empno) t
  on t.empno = e.empno
left join perf p on p.id = t.max_id;

-- 写法 B：相关子查询（可读性好，但每行执行一次）
select e.ename, p.level, p.ym
from emp e
left join perf p on p.id = (
  select p2.id from perf p2
  where p2.empno = e.empno
  order by p2.ym desc, p2.id desc
  limit 1
);

-- 写法 C：8.0 窗口函数（从表先排名，再取 rn = 1）
select e.ename, t.level, t.ym
from emp e
left join (
  select empno, level, ym,
         row_number() over (partition by empno order by ym desc, id desc) as rn
  from perf
) t on t.empno = e.empno and t.rn = 1;
```

- 三种写法结果一致，数据量大时 A 和 C 更稳；B 在从表数据多、主表行多时会退化成 N 次子查询。
- **不要写成 `left join perf p on p.empno = e.empno group by e.empno`** 来「随便取一条」：`group by` 下非聚合列的值在 `ONLY_FULL_GROUP_BY` 下非法，关掉该模式也只是「碰巧取到某一行」，不可靠。

#### 5.8 左 / 右外连接怎么选

判断口诀：**哪张表一行都不能少，就让它当左表用 `left join`**。如果它天然在右边，用 `right join`，或者调换表顺序改写成 `left join`（团队规范通常只允许 `left join`，便于阅读）。

| 需求 | 写法 |
| --- | --- |
| 部门列表要显示所有部门，包括没员工的 | `dept left join emp` |
| 员工列表要显示所有员工，包括没部门的 | `emp left join dept` |
| 以员工为主查考勤，没考勤也要显示 | `emp left join attendance` |
| 以考勤为主，没员工的考勤也要查（脏数据排查） | `attendance left join emp` |

**团队约定**：一个项目里统一只用 `left join`，`right join` 全部改写成调换表顺序的 `left join`，能显著降低「表顺序看错」导致的 bug。


### 6. 自连接

自连接不是一种新的 JOIN 语法，而是**同一张表在 `FROM` 里出现两次、用两个别名扮演两个角色**。适用于表内存在层级或关联关系的场景。

**硬性要求：必须起别名**，否则报 `Not unique table/alias: 'emp'`。

#### 6.1 场景一：员工 - 经理（最经典的面试题）

```sql
-- 每个员工和他的直属上级
select e.empno, e.ename, e.sal,
       m.ename as mgr_name, m.sal as mgr_sal
from emp e
left join emp m on e.mgr = m.empno
order by e.empno;
```

- 必须用 `left join` 才能保留没有上级的顶级员工（张三、孙七、周八的 `mgr` 为 NULL）；用 `join` 只剩 3 行。
- 查「工资比上级高的人」：

```sql
select e.ename as emp_name, e.sal, m.ename as mgr_name, m.sal as mgr_sal
from emp e
join emp m on e.mgr = m.empno
where e.sal > m.sal;
```

- 查「和谁同部门」（同表自连接 + 排除自己）：

```sql
select a.ename as name1, b.ename as name2
from emp a
join emp b on a.deptno = b.deptno and a.empno < b.empno;
```

`a.empno < b.empno` 是为了让 `(张三, 李四)` 和 `(李四, 张三)` 只出现一次；不加会得到对称的重复对，还会出现自己和自己配对。

#### 6.2 场景二：分类树 / 父子层级

表结构假设为 `category(id, name, parent_id)`：

```sql
-- 一级分类和它的子分类
select p.id as parent_id, p.name as parent_name,
       c.id as child_id,  c.name as child_name
from category p
join category c on c.parent_id = p.id;

-- 只查根节点（没有父分类的）
select c.* from category c
where not exists (select 1 from category p where p.id = c.parent_id);
```

自连接只能展开**固定层数**（一层一个 join），层数不定要用递归 CTE，见第 7 小节。

#### 6.3 场景三：找重复数据

```sql
-- 同一个邮箱注册了多个账号：直接列出冲突的两行（假设 users(id, email)）
select a.id as id1, b.id as id2, a.email
from users a
join users b on a.email = b.email and a.id < b.id;
```

对比 `group by email having count(*) > 1`：后者只能告诉你是哪个邮箱，拿不到具体冲突的 ID 对；自连接能直接定位到行，方便清理。

#### 6.4 场景四：相邻行比较

```sql
-- 与 empno 紧邻的上一位员工比工资（仅当 ID 连续时成立）
select cur.empno, cur.ename, cur.sal,
       prev.ename as prev_name, prev.sal as prev_sal,
       cur.sal - prev.sal as diff
from emp cur
join emp prev on cur.empno = prev.empno + 1;

-- 8.0 更稳的写法：窗口函数，不依赖 ID 连续
select empno, ename, sal,
       lag(ename) over (order by empno) as prev_name,
       sal - lag(sal) over (order by empno) as diff
from emp;
```

- `cur.empno = prev.empno + 1` 只在 ID 连续时成立，中间删过数据就会漏行；`lag()` / `lead()` 没有这个问题。
- 分组内比较要加 `partition by deptno`，否则会跨部门串行。

#### 6.5 场景五：同表内比聚合值

```sql
-- 比本部门平均工资高的员工：相关子查询版
select e.ename, e.sal, e.deptno
from emp e
where e.sal > (select avg(x.sal) from emp x where x.deptno = e.deptno);

-- 派生表版：先聚合再连接，只扫两遍表，大表更快
select e.ename, e.sal, d.avg_sal
from emp e
join (select deptno, avg(sal) as avg_sal from emp group by deptno) d
  on e.deptno = d.deptno
where e.sal > d.avg_sal;
```

#### 6.6 自连接、子查询、窗口函数怎么选

| 写法 | 适合场景 | 优点 | 代价 |
| --- | --- | --- | --- |
| 自连接 | 固定层级、同表两行比较、找重复 | 语义直白，连接列可走索引 | 表出现两次，别名容易写混 |
| 相关子查询 | 每行要和聚合值比较 | 逻辑清晰，不用起别名 | 外层每行执行一次子查询，大表慢 |
| 派生表 + join | 同表先聚合再比较 | 只扫两遍表，性价比高 | 需要多写一层子查询 |
| 窗口函数（8.0） | 排名、相邻行、组内聚合 | 一次扫描，性能最好 | 需 8.0+，语法门槛略高 |

### 7. 递归 CTE 查树（8.0+）

层级不定（组织架构、评论楼中楼、菜单树）时，自连接写不出来，用递归 CTE：

```sql
with recursive org as (
  -- 锚点：从没有上级的员工开始
  select empno, ename, mgr, 1 as lvl,
         cast(ename as char(200)) as path
  from emp
  where mgr is null

  union all

  -- 递归：把每个人的下属接到上一层
  select e.empno, e.ename, e.mgr, o.lvl + 1,
         concat(o.path, ' > ', e.ename)
  from emp e
  join org o on e.mgr = o.empno
)
select lvl, path from org order by path;
```

- 第一段是锚点（根），第二段是递归部分，两段用 `union all` 连接；写 `union` 会多做一次去重，白白变慢。
- **`path` 必须 `cast` 成足够长的类型**：递归 CTE 的列类型由第一段决定，不 cast 会按 `ename` 的长度截断或直接报错。
- 默认递归深度 `cte_max_recursion_depth = 1000`，层级过深或数据成环（a 的父是 b、b 的父是 a）会报 `Recursive query aborted after 1001 iterations`，需要 `SET SESSION cte_max_recursion_depth = 10000` 或先清洗环。
- 层级固定的 2 到 3 层，自连接更直观；读多写少的树，可以冗余 `path`（物化路径）或祖级 ID 列表字段，用 `like '1/3/%'` 查子树，避免递归。

### 8. 一次跑完的验证 SQL

```sql

drop table if exists dept;

create table dept (
  deptno int primary key,
  dname  varchar(20) not null
) default charset = utf8mb4;

insert into dept values (10, '研发'), (20, '市场'), (30, '财务'), (40, '新部门');

create table emp (
  empno  int primary key,
  ename  varchar(20) not null,
  deptno int,
  mgr    int,
  sal    decimal(10, 2),
  key idx_deptno (deptno),
  key idx_mgr (mgr)
) default charset = utf8mb4;

insert into emp values
  (1, '张三', 10,   NULL, 9000),
  (2, '李四', 10,   1,    8000),
  (3, '王五', 20,   1,    7500),
  (4, '赵六', 20,   3,    8000),
  (5, '孙七', 30,   NULL, 5000),
  (6, '周八', NULL, NULL, 4500);
```

```sql
-- ① 笛卡尔积：6 × 4 = 24
select count(*) as cnt from emp cross join dept;

-- ② 内连接：5 行（周八没有部门）
select e.ename, d.dname from emp e join dept d on e.deptno = d.deptno;

-- ③ 左连接：6 行（周八的 dname 为 NULL）
select e.ename, d.dname from emp e left join dept d on e.deptno = d.deptno;

-- ④ 等价改写：dept 左连接 emp，6 行（40 号部门的 ename 为 NULL）
select e.ename, d.dname from dept d left join emp e on e.deptno = d.deptno;

-- ⑤ 没有员工的部门：只有 40
select d.deptno, d.dname from dept d
left join emp e on e.deptno = d.deptno
where e.empno is null;

-- ⑥ 没有部门的员工：只有周八
select e.empno, e.ename from emp e
left join dept d on e.deptno = d.deptno
where d.deptno is null;

-- ⑦ 自连接找上级：left join 6 行，inner join 只有 3 行
select e.ename, m.ename as mgr_name from emp e left join emp m on e.mgr = m.empno;
select e.ename, m.ename as mgr_name from emp e join emp m on e.mgr = m.empno;

-- ⑧ 部门维度统计：40 号部门 cnt_star = 1、cnt_emp = 0
select d.deptno, d.dname, count(*) as cnt_star, count(e.empno) as cnt_emp
from dept d left join emp e on e.deptno = d.deptno
group by d.deptno, d.dname;
```

| 写法 | 行数 | 说明 |
| --- | --- | --- |
| `cross join` | 24 | 6 × 4 |
| 内连接 | 5 | 周八无部门，被排除 |
| `emp left join dept` | 6 | 保留周八，`dname` 为 NULL |
| `dept left join emp` | 6 | 保留 40 号部门，`ename` 为 NULL |
| 自连接 `join` | 3 | 只有李四、王五、赵六有上级 |
| 自连接 `left join` | 6 | 保留张三、孙七、周八 |

### 9. 性能：连接怎么写才不慢

- **被驱动表的连接列必须有索引**，否则每匹配一行就全表扫一次。本节 `emp.deptno`、`emp.mgr` 都建了索引，`EXPLAIN` 里 `type` 至少要到 `ref`，出现 `ALL` 就要查是不是缺索引。
- **驱动表选结果集小的那张**：优化器一般会自动选，但统计信息过期时会选错。可用 `straight_join` 强制左表驱动，或 8.0 的 `/*+ JOIN_ORDER(e, d) */` hint（8.0.20+）。`straight_join` 只控制顺序，不改变连接类型。
- **8.0.18+ 支持 hash join**：等值连接且被驱动表没索引时，`EXPLAIN` 的 Extra 会出现 `Using join buffer (hash join)`；5.7 是 `Block Nested Loop`，大表下性能差距很大。
- **连接列的类型、字符集、collation 必须完全一致**：`int` 连 `varchar`、`utf8` 连 `utf8mb4` 都会触发隐式转换，索引直接失效。这是线上慢查询最常见的隐形原因，建库统一 `utf8mb4` + `utf8mb4_0900_ai_ci`。
- `ON` 里不要对列套函数、不要写 `OR`：`on date(a.dt) = b.dt` 用不上索引，改成范围条件；`on a.id = b.id or a.code = b.code` 拆成两条 `union all`。
- **只取需要的列**：三表以上 `select *` 会把所有列拉进临时表，既费内存又破坏覆盖索引。
- 大表 join 后分页，先分页主表再关联（延迟关联），避免先把百万行连起来再 `limit`：

```sql
select e.empno, e.ename, d.dname
from (select empno, ename, deptno from emp order by empno limit 100000, 20) e
join dept d on e.deptno = d.deptno;
```

### 10. 易错点速记与工程建议

- **漏写连接条件 → 笛卡尔积**：n 张表至少 n - 1 个连接条件，多表查询写完先数一遍 `ON`。
- **自连接忘写别名** → `Not unique table/alias`；两个别名要能看出角色（`e` / `m`、`cur` / `prev`、`a` / `b`）。
- **左连接后在 `WHERE` 过滤右表列 → 退化成内连接**，要过滤右表就放 `ON`。
- **左连接后 `count(*)` 统计的是连接后的行数**，空关联也会贡献 1 行；统计左表用 `count(左表主键)`。
- **一对多连接会让 `SUM` 翻倍**：订单 join 明细后 `sum(订单金额)` 会按明细条数重复累加，正确做法是先聚合子表再连接，或直接对明细金额求和。
- **`NOT IN` 子查询含 NULL 时返回空集**，改用 `NOT EXISTS` 或反连接。
- **`NATURAL JOIN` 会随表结构变化悄悄改语义**，生产禁用；`USING` 至少写明列名。
- **外连接左右写反结果完全不同**：`a left join b` 不等于 `b left join a`，但等价于 `b right join a`。
- 多表同名列（`id`、`deptno`、`create_time`）必须用别名限定，否则报 `Column 'xxx' in field list is ambiguous`；应用层按列名取值时同名列还会互相覆盖。
- **外键不决定连接方式**：没有外键也能 join，有外键也不代表连接一定走索引。

**dev / prod 提示**：dev 端针对「漏 ON、左连接条件位置、`count(*)` 与 `count(列)`、一对多 SUM 翻倍」四类各造一组数据验证，用 `EXPLAIN` 核对 `type` 和 `rows`；prod 端连接列统一建索引并保证类型与字符集一致，禁止三表以上无索引 join 和 `select *`，大表分页用延迟关联，一对多统计先在子查询里聚合，上线前用 `EXPLAIN ANALYZE`（8.0.18+）对比实际行数与预估行数，偏差过大说明统计信息过期，先 `ANALYZE TABLE` 再判断执行计划。


## 表复制与数据去重

> 建测试库、做数据备份、大表改造、清理重复数据，都绕不开「复制表」和「去重」。这一节把两种操作的写法、差异和坑一次讲清。

### 1. 只复制表结构

| 方式 | 列定义 | 索引 | 自增属性 | 数据 |
| --- | --- | --- | --- | --- |
| `create table new like old;` | 复制 | **复制** | 复制，计数器从 1 开始 | 不复制 |
| `create table new as select * from old where 1 = 0;` | 按结果集推断 | 不复制 | 不复制 | 不复制 |

```sql
-- 推荐：完整复制结构（含索引、注释、字符集），不含外键
create table users_bak like users;

-- 只复制列，索引全丢，之后查询会慢
create table users_bak as select * from users where 1 = 0;
```

- `create table ... like` **不复制外键**定义，需要手动补。
- `create table ... as select` 是「按结果集建表」，列类型由查询结果推断，`varchar(64)` 可能变成 `varchar(64)` 也可能变 `text`，默认值、注释、`auto_increment` 都会丢。

### 2. 复制结构和数据

```sql
-- 方式一（推荐）：先 like 建结构，再 insert select 灌数据，索引完整
create table users_bak like users;
insert into users_bak select * from users;

-- 方式二：一条语句搞定，但只有数据没有索引
create table users_bak as select * from users;
```

- 方式二之后要补索引：`alter table users_bak add primary key (id), add key idx_email (email);`，否则备份表只能全表扫。
- `insert into ... select *` 依赖**列顺序完全一致**，线上表加过列就容易错位，规范写法是显式列出列名：

```sql
insert into users_bak (id, email, name, create_time)
select id, email, name, create_time from users;
```

### 3. 复制部分列 / 部分行

```sql
-- 只复制指定列（其余列走默认值）
insert into users_bak (id, email)
select id, email from users where status = 1;

-- 只复制最近 30 天（条件里用索引列，避免全表扫）
insert into users_bak (id, email, name, create_time)
select id, email, name, create_time
from users
where create_time >= date_sub(now(), interval 30 day);
```

### 4. 写入已存在的表

```sql
-- 目标表已有数据，追加
insert into users_bak (id, email, name) select id, email, name from users;

-- 遇到主键/唯一键冲突时：
-- insert ignore        忽略冲突行
-- replace into         先删后插（会丢未指定的列）
-- on duplicate key update  按需更新，推荐
```

三种冲突处理在「主键、唯一约束与外键」第 3.1 小节有对照表，复制场景优先用 `on duplicate key update`，避免 `replace` 把整行重置。

### 5. 跨库、跨实例复制

```sql
-- 同一个实例的两个库
insert into db2.users (id, email, name)
select id, email, name from db1.users;
```

```bash
# 跨实例：导出再导入
mysqldump -u root -p --single-transaction --set-gtid-purged=OFF db1 users > users.sql
mysql -u root -p db2 < users.sql
```

- `--single-transaction` 让 InnoDB 导出走一致性快照，不锁表。
- 大文件导入前临时 `set foreign_key_checks = 0;`，导入后记得改回来。
- 服务端文件导入导出（`load data infile` / `select into outfile`）受 `secure_file_priv` 限制，8.0 默认只允许指定目录，云数据库通常直接禁用，改用客户端工具或 `mysqldump`。

### 6. 大表分批复制

一次性 `insert into ... select *` 几十万行会撑大事务、写满 undo、拉高主从延迟。按主键分批：

```sql
-- 每批 1000 行，记录上一批的最大 id，循环执行
insert into users_bak (id, email, name, create_time)
select id, email, name, create_time
from users
where id > 0
order by id
limit 1000;

-- 下一批把条件换成上一批查到的最大 id
-- where id > 1000 order by id limit 1000
```

- 批大小 500 到 2000 比较稳，太大容易锁等待，太小事务开销高。
- 复制期间新写入的数据会在最后一批之后，收尾时用 `where id > 最后一批的 id` 再补一次，或直接锁表短暂补齐。

### 7. 查询去重

| 方法 | 语法 | 说明 |
| --- | --- | --- |
| `distinct` | `select distinct email from users;` | 整行比较去重，NULL 视为相同 |
| `distinct` 多列 | `select distinct email, phone from users;` | 按 (email, phone) 组合去重 |
| `group by` | `select email from users group by email;` | 可同时带聚合，如 `count(*)` |
| `count(distinct)` | `select count(distinct email) from users;` | 去重计数，跳过 NULL |
| 窗口函数 | `row_number() over (partition by email order by id)` | 8.0+，能标记保留哪一条 |

```sql
-- 先查清楚有哪些重复、重复几次、涉及哪些 id，再动手删
select email, count(*) as cnt, group_concat(id order by id) as ids
from users
group by email
having count(*) > 1;
```

- `distinct` 作用在**整行**，不是第一列；`select distinct a, b` 是 `(a, b)` 组合去重，容易和「按 a 去重」混淆。
- MySQL 8.0 里 `select distinct email from users order by name` 会报错（3065）：`ORDER BY` 的表达式必须出现在 select 列表里。要么把排序列加进 select，要么改用 `group by`。
- `count(distinct a, b)` 可以按多列组合计数，但 `count(distinct *)` 不合法。

### 8. 删除重复数据，每组保留一条

#### 8.1 小表：自连接删除

```sql
-- 保留每组 id 最小的那条，删除其余
delete t1 from users t1
join users t2 on t1.email = t2.email and t1.id > t2.id;
```

- `t1.id > t2.id` 是关键：它保证同组内只有「id 不是最小」的行被删；写成 `t1.id <> t2.id` 会把整组都删掉。
- 想保留最大的就改成 `t1.id < t2.id`。
- 多列判定重复：`on t1.email = t2.email and t1.phone = t2.phone and t1.id > t2.id`。
- **NULL 不参与 `=` 比较**：`t1.email = t2.email` 对 NULL 不成立，所以含 NULL 的行不会被判为重复；要连 NULL 一起判定，用 `t1.email <=> t2.email`（安全等于）。

#### 8.2 大表：建新表 + 原子切换

大表直接 `delete` 会产生大事务、长时间锁、主从延迟，正确姿势是「查出保留的 id → 灌新表 → rename 切换」：

```sql
-- 1. 建同结构新表
create table users_new like users;

-- 2. 每组只灌 id 最小的那条
insert into users_new (id, email, name, create_time)
select u.id, u.email, u.name, u.create_time
from users u
join (select min(id) as min_id from users group by email) t
  on u.id = t.min_id;

-- 3. 核对行数：原表去重后的数量应与新表一致
select (select count(*) from users)                                    as old_cnt,
       (select count(*) from users_new)                                as new_cnt,
       (select count(distinct email) from users)                       as distinct_cnt;

-- 4. 原子切换（一条语句完成，业务无感知）
rename table users to users_bak, users_new to users;
```

- `rename table` 是原子的，切换瞬间不会出现表不存在。
- 切换后保留 `users_bak` 至少一天，确认业务正常再删。
- 新表如果还有自增列，`insert` 时显式写入了原 id，8.0 会自动把自增计数器调到 `max(id) + 1`，不需要手动 `alter`。
- 新表没有外键时，依赖外键的应用要检查一遍；`create table like` 不复制外键，需要手动补。

### 9. 验证 SQL（可直接跑）

```sql
drop table if exists users;

create table users (
  id    bigint unsigned not null auto_increment primary key,
  email varchar(64) not null,
  name  varchar(32) not null
) engine = InnoDB default charset = utf8mb4;

insert into users (email, name) values
  ('a@x.com', '张三'),
  ('a@x.com', '张三丰'),
  ('b@x.com', '李四'),
  ('b@x.com', '李四'),
  ('c@x.com', '王五');

-- 5 行，其中 a、b 各重复一次
select count(*) from users;

-- 查出重复：a@x.com 2 条（1,2），b@x.com 2 条（3,4）
select email, count(*) as cnt, group_concat(id order by id) as ids
from users group by email having count(*) > 1;

-- 去重后应该是 3 行
select count(distinct email) from users;

-- 执行删除，保留每组最小 id
delete t1 from users t1
join users t2 on t1.email = t2.email and t1.id > t2.id;

-- 验证：3 行，id 为 1、3、5
select id, email, name from users order by id;
```

### 10. 易错点与工程建议

- **`create table ... as select` 丢索引**：备份表、临时表都变全表扫，数据量大时排查半天；用 `like` + `insert select` 更稳。
- **`insert into ... select *` 依赖列顺序**：源表加列后目标表错位，报错或写错数据；一律显式列名。
- **`replace into` 当 upsert**：会先删整行，未指定的列被重置为默认值，自增 id 变化，触发器也会跑。
- **`distinct` 不是「按第一列去重」**：它是整行去重，多列时按组合判断。
- **`distinct` 搭配 `order by` 非 select 列会报 3065**，改 `group by` 或把列加进 select。
- **删重复忘了 `t1.id > t2.id`**：整组被删光，只能靠备份恢复。
- **大表直接 `delete` 去重**：大事务、锁表、主从延迟、undo 膨胀，一律走「新表 + rename」。
- **复制表后自增冲突**：显式插入原 id 时不会冲突，但如果只复制部分数据、之后两边都继续写入，合并时会撞主键，需要预留 ID 段或改用新 ID。
- **跨库复制忽略字符集**：源库 utf8、目标库 utf8mb4 时可能出现乱码或截断，复制前确认两边字符集一致。
- **忘记备份**：任何删除操作前先 `create table xxx_bak like xxx` + `insert select`，或在事务里先 `select` 确认影响行数。

**dev / prod 提示**：dev 端随便用 `create table as select` 造数据没问题，但要知道它没索引；prod 端所有「复制表」操作都按 `like` + 显式列 + 分批 + 校验行数四步走，去重一律先 `select` 统计、再建新表、再 `rename` 切换，保留旧表至少一天。删除类操作先在从库或影子库演练，记录 `select count(*)` 前后对比，`delete` 语句必须带 `where` 并先 `select` 验证条件命中行数。


## mysql事务

> 下面保留原有的事务定义和 5 条控制语句（修正了 `transcation` 拼写和注释写法），并补全 ACID、四种隔离级别、MVCC 原理、两会话实测、长事务排查和 Spring 集成。面试里「MySQL 默认隔离级别 + 幻读怎么解决 + MVCC」基本是必问三连。

### 1. 什么是事务

事务用于保证数据的一致性，它由一组关键的 DML 语句组成，这组语句**要么全部成功，要么全部失败**。典型例子是转账：A 扣 100、B 加 100，两条 `update` 必须同生共死。

```sql
start transaction;
update account set balance = balance - 100 where id = 1;
update account set balance = balance + 100 where id = 2;
commit;
```

InnoDB 支持事务，MyISAM 不支持（这也是 MyISAM 逐渐被淘汰的主因之一）。

### 2. ACID 与实现

| 特性 | 含义 | InnoDB 靠什么实现 |
| --- | --- | --- |
| 原子性 Atomicity | 要么全成功，要么全失败 | undo log（回滚日志） |
| 一致性 Consistency | 数据从一个合法状态到另一个合法状态 | 由另外三个特性 + 约束共同保证 |
| 隔离性 Isolation | 并发事务互不干扰 | 锁 + MVCC |
| 持久性 Durability | 提交后断电也不丢 | redo log + 刷盘（`innodb_flush_log_at_trx_commit = 1`） |

面试常问「ACID 分别怎么实现」，答案其实只有三个组件：**undo log 管原子性，redo log 管持久性，锁和 MVCC 管隔离性**，一致性是结果而不是手段。

### 3. 事务控制语句

| 语句 | 作用 |
| --- | --- |
| `start transaction;` / `begin;` | 开始一个事务 |
| `savepoint 保存点名;` | 设置保存点 |
| `rollback to 保存点名;` | 回退到保存点，**事务并未结束** |
| `release savepoint 保存点名;` | 删除保存点 |
| `rollback;` | 回退全部事务 |
| `commit;` | 提交事务，所有操作生效，不能回退 |

```sql
start transaction;
update account set balance = balance - 100 where id = 1;
savepoint after_out;          -- 记一个点
update account set balance = balance + 100 where id = 2;
rollback to after_out;        -- 只撤销 B 的加钱，A 的扣钱还在
commit;                       -- 提交 A 的扣钱
```

- `set autocommit = 0;` 关闭自动提交后，每条 DML 都会隐式开启事务，直到 `commit` / `rollback`。Java 连接池一般保持 `autocommit = 1`，由 Spring 显式控制。
- `rollback to` 执行后保存点仍然存在，可以再回滚一次；`release savepoint` 之后就不能再回到它了。
- 保存点只能回滚 DML，**回滚不了 DDL**（DDL 会隐式提交，见第 8 小节）。

### 4. 并发事务会带来什么问题

| 问题 | 定义 | 例子 |
| --- | --- | --- |
| 脏读 | 读到了别的事务**未提交**的数据 | A 把余额改成 500 还没提交，B 读到了 500；A 回滚后 B 拿到的是假数据 |
| 不可重复读 | 同一事务内两次读**同一行**，结果不同 | A 第一次读余额 1000，B 改成 900 并提交，A 再读变成 900 |
| 幻读 | 同一事务内两次**范围查询**，行数不同 | A 查 `id > 10` 是空，B 插入 id=11 并提交，A 再查多出一行 |
| 更新丢失 | 两个事务读同一行后各自改写，后写的覆盖先写的 | 库存 10，A、B 都读到 10 各减 1，最终是 9 而不是 8 |

- 不可重复读针对**同一行被修改**，幻读针对**结果集行数变化**（别人插入或删除），两者容易混，记住「一行」和「一批」的区别。
- 更新丢失在 MySQL 的 RR / RC 下一般不会发生（`update` 是当前读，会加行锁串行化），但「先查出来算好再写回去」的业务逻辑仍会丢更新，要用 `update ... set x = x - 1` 或乐观锁版本号。

### 5. 四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 读的实现 |
| --- | --- | --- | --- | --- |
| `READ UNCOMMITTED` | 可能 | 可能 | 可能 | 不加快照，直接读最新数据 |
| `READ COMMITTED` | 不会 | 可能 | 可能 | 每次快照读都生成新的 ReadView |
| `REPEATABLE READ` | 不会 | 不会 | 快照读不会，当前读靠间隙锁避免 | 事务内第一次快照读生成 ReadView 后复用 |
| `SERIALIZABLE` | 不会 | 不会 | 不会 | 读也加共享锁，事务串行执行 |

- **MySQL InnoDB 默认是 `REPEATABLE READ`**，而 SQL 标准默认是 `SERIALIZABLE`、Oracle 默认是 `READ COMMITTED`。这是面试高频对比点。
- 级别越高，一致性越强、并发越差。`SERIALIZABLE` 下普通 `select` 也会加共享锁，读写互相阻塞，生产环境几乎不用。
- 不少互联网公司会主动改成 `READ COMMITTED`（阿里云 RDS 默认就是 RC），原因是 RC 不加大范围的间隙锁，死锁更少、并发更高、主从延迟更小；代价是可能出现不可重复读和幻读，需要业务自己兜。

```sql
-- 查看当前会话的隔离级别（8.0）
select @@transaction_isolation;

-- 5.7 及以前用这个变量名
select @@tx_isolation;

-- 设置当前会话
set session transaction isolation level read committed;

-- 设置全局（只对之后新建的连接生效，已存在的连接不变）
set global transaction isolation level repeatable read;
```

> 连接池的坑：`set global` 只影响新连接，池子里的旧连接仍是老级别。改完要重启应用或让连接池回收，否则会出现「一部分连接是 RC、一部分是 RR」的诡异现象。

### 6. MVCC：RC 和 RR 到底差在哪

MVCC（多版本并发控制）让「读不加锁、读写不阻塞」，是 RC 和 RR 的核心实现。

#### 6.1 版本链

InnoDB 每行有两个隐藏列：

- `DB_TRX_ID`：最后一次修改这行的事务 ID。
- `DB_ROLL_PTR`：指向 undo log 中该行的上一个版本。

每次 `update` 都会把旧版本写进 undo log，并用回滚指针串成链表，形成**版本链**，链头是最新版本。

#### 6.2 ReadView

快照读时生成一个 ReadView，包含四个关键字段：

| 字段 | 含义 |
| --- | --- |
| `m_ids` | 生成 ReadView 时所有**活跃（未提交）**事务的 ID 列表 |
| `min_trx_id` | `m_ids` 中的最小值 |
| `max_trx_id` | 下一个将要分配的事务 ID（当前最大 ID + 1） |
| `creator_trx_id` | 当前事务自己的 ID |

可见性判断（拿版本链上某个版本的 `trx_id` 逐条比对）：

1. 等于 `creator_trx_id`：自己改的，可见。
2. 小于 `min_trx_id`：ReadView 生成前就已提交，可见。
3. 大于等于 `max_trx_id`：ReadView 生成后才开启的事务，不可见。
4. 介于两者之间：在 `m_ids` 里说明还没提交，不可见；不在则已提交，可见。

不可见就顺着回滚指针找上一个版本，直到找到可见版本或链表结束。

#### 6.3 RC 与 RR 的唯一区别

| 级别 | ReadView 生成时机 | 结果 |
| --- | --- | --- |
| `READ COMMITTED` | **每条 `select` 都重新生成** | 能看到别人新提交的数据，所以不可重复读 |
| `REPEATABLE READ` | **事务内第一条 `select` 生成，之后复用** | 整个事务看到同一份快照，所以可重复读 |

一句话：**MVCC 的机制完全一样，差别只在 ReadView 生成几次**。

#### 6.4 快照读与当前读

| 类型 | 语句 | 读什么 |
| --- | --- | --- |
| 快照读 | 普通 `select` | 按 ReadView 读历史版本，不加锁 |
| 当前读 | `select ... for update`、`select ... lock in share mode`、`update`、`delete`、`insert` | 读最新已提交版本，并加锁 |

- `update` / `delete` 也是当前读，所以它们总能看到最新数据，这也是「RR 下快照读看不到、但 update 能改到」的原因。
- 同一事务里混用快照读和当前读，会出现「查的时候没有、改的时候有了」的割裂感，业务代码要避免。

### 7. 幻读与间隙锁

RR 下的幻读分两种情况：

- **纯快照读**：靠 MVCC 就不会幻读，因为整个事务用同一个 ReadView。
- **当前读**（`for update`、`update`、`delete`）：读的是最新数据，别人新插入的行会被看到，所以需要**间隙锁**。

InnoDB 的锁粒度：

| 锁 | 锁什么 |
| --- | --- |
| Record Lock | 索引上的单条记录 |
| Gap Lock | 两条索引记录之间的间隙（左开右开） |
| Next-Key Lock | Record Lock + Gap Lock，左开右闭，RR 的默认行锁形式 |

```sql
-- RR 下，这条当前读会锁住 (10, +∞) 这个区间
select * from account where id > 10 for update;
-- 此时另一个事务插入 id = 11 会被阻塞，直到上面的事务提交
```

- **RC 下间隙锁基本关闭**（只在唯一性检查和外键检查时短暂使用），所以 RC 并发更高、死锁更少，但当前读会幻读。
- RR 的间隙锁范围可能比想象中大（走不到索引时会锁住全表的记录和间隙），这也是 RR 死锁率更高的原因。
- 死锁排查：`show engine innodb status;` 看 `LATEST DETECTED DEADLOCK` 段。

### 8. 哪些操作会隐式提交

以下语句执行前会**自动提交当前事务**，`rollback` 也救不回来：

| 类别 | 语句 |
| --- | --- |
| DDL | `create` / `alter` / `drop` / `rename` / `truncate` |
| 锁表 | `lock tables` / `unlock tables` |
| 权限与账户 | `grant` / `revoke` / `create user` / `drop user` |
| 事务控制 | `start transaction`（会先提交上一个事务） |
| 自动提交开关 | `set autocommit = 1` |
| 维护 | `analyze table` / `optimize table` / `repair table` |

- **`truncate` 是 DDL，不能回滚**，删数据要用 `delete`（可回滚，但慢）。
- 事务里混入 DDL 是经典事故：前面一堆 DML 被悄悄提交，后面的 `rollback` 只回滚了 DDL 之后的部分。

### 9. 长事务与大事务

危害：

- undo log 无法清理，版本链越来越长，快照读越读越慢，表空间膨胀。
- 持有锁时间长，阻塞其他事务，死锁概率上升。
- 主从延迟（大事务在从库重放耗时长）。
- 回滚极慢（要反向执行所有 undo）。

排查：

```sql
select trx_id,
       trx_state,
       trx_started,
       timestampdiff(second, trx_started, now()) as duration_sec,
       trx_rows_locked,
       trx_rows_modified,
       trx_mysql_thread_id,
       trx_query
from information_schema.innodb_trx
order by trx_started
limit 10;

-- 找到长事务后 kill 掉对应连接
-- kill 12345;
```

规避：

- 事务里只放 DB 操作，**不要放 RPC、HTTP 调用、文件 IO、大批量循环**。
- 大批量写入拆成小批，每批 500 到 2000 行，单独提交。
- 把「先查询再判断」的逻辑尽量前移，缩短事务持有时间。
- 设置 `innodb_lock_wait_timeout`（默认 50 秒）和 `@Transactional(timeout = ...)`，避免无限等待。
- 监控：对 `innodb_trx` 里 `duration_sec > 60` 的事务告警。

### 10. Spring 中的事务与隔离级别

```java
@Service
public class TransferService {

    @Transactional(
        rollbackFor = Exception.class,           // 检查异常也回滚
        isolation = Isolation.REPEATABLE_READ,   // 不写则跟随数据库（MySQL 是 RR）
        propagation = Propagation.REQUIRED,      // 默认：有事务就加入，没有就新建
        timeout = 30,                            // 超时秒数
        readOnly = false
    )
    public void transfer(Long from, Long to, BigDecimal amount) {
        accountMapper.decrease(from, amount);
        accountMapper.increase(to, amount);
    }
}
```

| 配置 | 说明 |
| --- | --- |
| `isolation` | 默认 `Isolation.DEFAULT`，即用数据库的级别；显式指定会覆盖 |
| `propagation` | 默认 `REQUIRED`；`REQUIRES_NEW` 会挂起当前事务另开一个 |
| `rollbackFor` | 默认只回滚 `RuntimeException` 和 `Error`，**检查异常不回滚**，必须显式写 `Exception.class` |
| `readOnly` | 只读事务，让驱动跳过不必要的处理，也能防止误写 |

`@Transactional` 失效的常见原因：

1. **同类内部方法调用**：`this.method()` 不走代理，注解不生效。
2. 方法不是 `public`，代理不拦截。
3. 异常被 `catch` 吃掉，容器感知不到。
4. 抛出的是检查异常且没配 `rollbackFor`。
5. 类没有被 Spring 管理（自己 `new` 出来的）。
6. 多线程调用：事务绑定在 ThreadLocal 上，子线程不在同一事务。
7. 表引擎是 MyISAM（不支持事务）。

- 传播行为 `REQUIRES_NEW` 要特别注意：它会**挂起外层事务、新开一个连接**，如果外层持有行锁、内层又要改同一行，直接死锁。
- 事务方法里不要吞异常：`catch` 之后要么重新抛，要么 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`。

### 11. 两个会话实测（可复现）

准备数据：

```sql
drop table if exists account;
create table account (
  id      int primary key,
  balance decimal(12, 2) not null
) engine = InnoDB default charset = utf8mb4;

insert into account values (1, 1000.00), (2, 1000.00);
```

#### 11.1 脏读（READ UNCOMMITTED）

```sql
-- 会话 A
set session transaction isolation level read uncommitted;
start transaction;
select balance from account where id = 1;          -- 1000

-- 会话 B
start transaction;
update account set balance = 500 where id = 1;     -- 未提交

-- 会话 A
select balance from account where id = 1;          -- 500，脏读

-- 会话 B
rollback;

-- 会话 A
select balance from account where id = 1;          -- 回到 1000，刚才读到的是脏数据
commit;
```

#### 11.2 不可重复读（READ COMMITTED）

```sql
-- 会话 A
set session transaction isolation level read committed;
start transaction;
select balance from account where id = 1;          -- 1000

-- 会话 B
update account set balance = 900 where id = 1;
commit;

-- 会话 A
select balance from account where id = 1;          -- 900，同一事务内前后不一致
commit;
```

#### 11.3 可重复读 + 快照读与当前读的差异（REPEATABLE READ）

```sql
-- 会话 A
set session transaction isolation level repeatable read;
start transaction;
select balance from account where id = 1;          -- 1000

-- 会话 B
update account set balance = 800 where id = 1;
commit;

-- 会话 A
select balance from account where id = 1;                  -- 仍是 1000（快照读）
select balance from account where id = 1 for update;       -- 800（当前读）
commit;
```

这个对比最能说明 MVCC：**同一个事务里，普通 select 看历史版本，for update 看最新版本**。

#### 11.4 幻读与间隙锁

```sql
-- 会话 A
start transaction;
select * from account where id > 10;               -- 空

-- 会话 B
insert into account (id, balance) values (11, 100);
commit;

-- 会话 A
select * from account where id > 10;               -- 仍为空（快照读，MVCC 防住了）
select * from account where id > 10 for update;    -- 出现了 id = 11，发生幻读
commit;
```

```sql
-- 会话 A：先当前读，锁住 (10, +∞)
start transaction;
select * from account where id > 10 for update;

-- 会话 B：插入会阻塞，直到 A 提交（间隙锁生效）
insert into account (id, balance) values (12, 100);
```

### 12. 易错点与 dev / prod 建议

- **以为 RR 完全不会幻读**：快照读不会，当前读配合间隙锁也能防住，但「先快照读、再当前读」的混用仍会看到新行。
- **以为 `rollback` 能回滚一切**：DDL、`truncate`、`lock tables` 都会隐式提交，回滚不了。
- **事务里混 DDL**：前面的 DML 被悄悄提交，排查时以为是「回滚失效」。
- **`@Transactional` 加在同类方法上**：内部调用不走代理，注解白写；要么拆到另一个 Bean，要么用 `AopContext.currentProxy()`。
- **默认只回滚 `RuntimeException`**：业务抛检查异常时不回滚，必须 `rollbackFor = Exception.class`。
- **改隔离级别只改了 global**：连接池里的旧连接不生效，要重启或回收连接。
- **RC + statement 格式 binlog**：主从可能不一致，RC 必须配 `binlog_format = ROW`。
- **长事务拖垮库**：定时任务里一个循环包一个事务，几万行下来 undo 膨胀，务必分批提交。
- **`select ... for update` 当普通查询用**：它加的是排他锁，并发下直接排队甚至死锁，只在「读后要改」时用。
- `innodb_lock_wait_timeout` 默认 50 秒，业务等不起，按接口超时调小（如 5 秒）并做好重试。

**dev / prod 提示**：dev 端开两个客户端窗口把第 11 小节的四组实验各跑一遍，把 `innodb_lock_wait_timeout` 调到 5 秒便于观察锁等待，用 `show engine innodb status` 看锁信息。prod 端默认保持 RR（或按业务改 RC 并确认 `binlog_format = ROW`），事务里禁止 RPC 和大查询，批量操作分批提交，给 `innodb_trx` 里超过 60 秒的事务配告警，接口层设置合理超时与幂等，避免「事务没提交、用户已重试」造成的重复写入。
