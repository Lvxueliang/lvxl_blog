# 反射 Reflection

## 一、反射是什么（面试开场第一问）

1. 反射机制允许程序在**执行期间**借助于 Reflection API 获取任何类的内部信息（类名、方法名、属性名、构造器、注解等），并能操作对象的属性和方法。
2. 加载完类之后，在**堆**中就会产生一个 `Class` 类型的对象（一个类只有一个 Class 对象）。这个对象包含了类的完整结构信息，通过这个对象得到类的结构。

一句话答面试官：**反射就是把「类」本身也当成对象来操作 —— 运行期才知道要操作谁，而不是编译期写死。**

| | 正射（常规） | 反射 |
| --- | --- | --- |
| 时机 | 编译期确定类型 | 运行期才确定类型 |
| 写法 | `new Cat().hi()` | `Class.forName("...Cat").getMethod("hi").invoke(obj)` |
| 前提 | 必须有源码/编译依赖 | 只要有类名（字符串）即可 |
| 性能 | 快，可被 JIT 内联 | 慢，有额外开销 |
| 安全 | 编译期检查 | 可绕过访问控制，破坏封装 |

反射的核心包：`java.lang.reflect`，核心类：

| 类 | 代表什么 |
| --- | --- |
| `Class<T>` | 类本身（反射入口） |
| `Method` | 方法 |
| `Field` | 字段/属性 |
| `Constructor<T>` | 构造器 |
| `Modifier` | 修饰符（static/final/public 判断） |
| `Array` | 动态创建和访问数组 |
| `Proxy` / `InvocationHandler` | 动态代理 |

## 二、为什么需要反射（讲义示例）

需求：不修改源码，只改配置文件，就能决定「实例化哪个类、调用哪个方法」。

`re.properties`：

```txt
classfullpath=com.hspedu.Cat
method=cry
```

```java
public class ReflectionQuestion {

    public static void main(String[] args) throws Exception {
        // 根据配置文件 re.properties 指定信息，创建 Cat 对象并调用方法
        // 传统方式：new 对象 => 调用方法，改需求要改源码
        // Cat cat = new Cat();
        // cat.hi(); ==> cat.cry(); 修改源码

        // 1. 使用 Properties 类读写配置文件
        Properties properties = new Properties();
        properties.load(new FileInputStream("src/re.properties"));
        String classfullpath = properties.get("classfullpath").toString();
        String methodName = properties.get("method").toString();
        System.out.println("classfullpath=" + classfullpath);
        System.out.println("method=" + methodName);

        // 2. 传统方式行不通：new classfullpath(); 类名是运行时才拿到的字符串
        // 框架里特别多这种「外部文件配置 + 不改源码」的写法，
        // 符合设计模式的 OCP（开闭原则）：对扩展开放、对修改关闭

        // 3. 用反射机制解决
        // (1) 加载类，返回 Class 类型的对象
        Class<?> cls = Class.forName(classfullpath);
        // (2) 通过 cls 得到 Cat 的对象实例
        Object o = cls.newInstance();   // 注意：此写法 JDK 9 起已废弃，见第五节
        System.out.println("o 的运行类型=" + o.getClass());
        // (3) 通过 cls 得到 methodName 对应的方法对象 —— 反射中「方法也是对象」
        Method method1 = cls.getMethod(methodName);
        // (4) 通过方法对象调用：传统是「对象.方法()」，反射是「方法.invoke(对象)」
        method1.invoke(o);
    }
}
```

配套的 `Cat`：

```java
package com.hspedu;

public class Cat {
    private String name = "招财猫";

    public void hi() {
        System.out.println("hi " + name);
    }

    public void cry() {
        System.out.println("喵喵叫 " + name);
    }
}
```

> 小建议：`properties.get(k)` 返回 `Object`，取字符串属性用 `getProperty(k)` 更直接，也避免了 `null.toString()` 的 NPE。

## 三、获取 Class 对象的四种方式（★★★★★ 必考）

| 方式 | 写法 | 是否触发类初始化（执行静态代码块） | 场景 |
| --- | --- | --- | --- |
| 类名.class | `Class<Cat> c = Cat.class;` | **否** | 编译期已知类型，最安全高效 |
| 对象.getClass() | `Class<?> c = obj.getClass();` | 已初始化（对象都有了） | 已有实例，想拿它的运行类型 |
| Class.forName(全限定名) | `Class<?> c = Class.forName("com.hspedu.Cat");` | **是**（默认 `initialize=true`） | 配置文件、框架、JDBC 驱动 |
| 类加载器.loadClass | `Class<?> c = loader.loadClass("com.hspedu.Cat");` | **否**（只加载不初始化） | 懒加载、需要精细控制时 |

```java
// 第四种：类加载器方式，可指定是否初始化
ClassLoader loader = ClassLoader.getSystemClassLoader();
Class<?> c4 = loader.loadClass("com.hspedu.Cat");            // 不初始化
Class<?> c5 = Class.forName("com.hspedu.Cat", false, loader); // 显式不初始化
```

**为什么这个区别重要**：`Class.forName` 会执行静态代码块，而老的 JDBC 写法正是靠这一点注册驱动的：

```java
Class.forName("com.mysql.cj.jdbc.Driver"); // 触发 static { DriverManager.registerDriver(...) }
```

JDBC 4.0 之后有了 SPI 自动发现，这一句其实可以省略，但面试常拿它举例。

其他特殊类型：

```java
int.class == Integer.TYPE          // true，基本类型也有 Class 对象
Integer.class == int.class         // false！
String[].class                     // 数组的 Class
Class.forName("[I")                // int[] 的 Class
void.class                         // void
```

**结论**：同一个类在 JVM 中**只有一个 Class 对象**，四种方式拿到的都是同一个引用，`==` 为 true。所以拿它做缓存 key 是安全的。

## 四、获取类结构：getXxx 与 getDeclaredXxx（★★★★★ 必考）

| 方法 | 返回内容 | 含非 public | 含继承 |
| --- | --- | --- | --- |
| `getFields()` | 字段数组 | ❌ 只 public | ✅ 含父类 public |
| `getDeclaredFields()` | 字段数组 | ✅ 全部 | ❌ 只本类 |
| `getMethods()` | 方法数组 | ❌ 只 public | ✅ 含父类 public（含 Object 的） |
| `getDeclaredMethods()` | 方法数组 | ✅ 全部 | ❌ 只本类 |
| `getConstructors()` | 构造器数组 | ❌ 只 public | 构造器不被继承 |
| `getDeclaredConstructors()` | 构造器数组 | ✅ 全部 | 构造器不被继承 |
| `getSuperclass()` | 父类 Class | — | — |
| `getInterfaces()` | 实现的接口 | — | 只直接实现 |
| `getPackage()` / `getName()` / `getSimpleName()` | 包/全限定名/简单名 | — | — |
| `getAnnotations()` | 运行期可见的注解 | — | 需要 `@Retention(RUNTIME)` |

一句话记住规律：**带 `Declared` 的能看私有、但只看本类；不带 `Declared` 的只看 public、但会往父类找。**

```java
Class<?> cls = Cat.class;

Field[] pubFields   = cls.getFields();          // 只有 public，含继承
Field[] allFields   = cls.getDeclaredFields();  // 本类所有，含 private
Method[] pubMethods = cls.getMethods();         // 含 Object 的 11 个方法
Method[] allMethods = cls.getDeclaredMethods(); // 只看本类

for (Method m : allMethods) {
    // 用 Modifier 判断修饰符，比解析字符串靠谱
    System.out.println(Modifier.toString(m.getModifiers()) + " " + m.getName());
}
```

## 五、创建实例与调用成员

### 1. 创建实例的两种写法

```java
// 老写法：JDK 9 起 @Deprecated（只能用无参构造，且抛出的异常信息含糊）
Object o1 = cls.newInstance();

// 推荐写法：JDK 9+ 官方建议，能选构造器，异常也更准确
Object o2 = cls.getDeclaredConstructor().newInstance();

// 带参构造
Constructor<?> ctor = cls.getDeclaredConstructor(String.class);
Object o3 = ctor.newInstance("加菲猫");
```

`newInstance()` 被废弃的原因：它把构造器抛出的异常都包成 `InstantiationException`/`IllegalAccessException`，看不出真实原因；新写法会把原始异常抛出来。

### 2. 调用方法

```java
Method hi = cls.getMethod("hi");            // public 方法
hi.invoke(obj);                              // 静态方法则传 null
Method setName = cls.getMethod("setName", String.class); // 参数类型要精确匹配
setName.invoke(obj, "汤姆");
```

### 3. 读写字段

```java
Field nameField = cls.getDeclaredField("name"); // 私有字段必须用 Declared
nameField.setAccessible(true);                  // 关闭访问检查
Object v = nameField.get(obj);
nameField.set(obj, "新名字");

// 静态字段：对象参数传 null
Field countField = cls.getDeclaredField("count");
countField.setAccessible(true);
countField.set(null, 10);
```

### 4. 一个完整可运行示例

```java
class User {
    private String name;
    private int age;
    private static int total;

    private User() {}
    public User(String name, int age) { this.name = name; this.age = age; }
    private String hello(String prefix) { return prefix + name; }
    public int getAge() { return age; }
}

public class ReflectDemo {
    public static void main(String[] args) throws Exception {
        Class<?> cls = Class.forName("User");

        // 私有构造也能造对象
        Constructor<?> ctor = cls.getDeclaredConstructor(String.class, int.class);
        Object user = ctor.newInstance("张三", 20);

        // 私有方法
        Method hello = cls.getDeclaredMethod("hello", String.class);
        hello.setAccessible(true);
        System.out.println(hello.invoke(user, "你好，")); // 你好，张三

        // 私有字段
        Field age = cls.getDeclaredField("age");
        age.setAccessible(true);
        age.set(user, 28);
        System.out.println(age.get(user)); // 28

        // 静态字段
        Field total = cls.getDeclaredField("total");
        total.setAccessible(true);
        total.set(null, 1);
    }
}
```

## 六、setAccessible：暴力反射与它的边界（★★★★ 常考）

`setAccessible(true)` 的作用是**关闭 Java 语言的访问权限检查**（`AccessibleObject` 里的 `override` 标志），让私有成员可以被读写调用。

三个必须知道的点：

1. **性能上反而更快**：关闭检查后省掉每次调用的权限校验，所以「反射慢」的场景里它常被当作优化手段。
2. **JDK 9 引入模块系统后开始受限**：反射访问 JDK 内部 API（如 `java.lang` 里的非公开成员、`sun.*`）会抛 `InaccessibleObjectException`，需要启动参数显式开放：

```bash
java --add-opens java.base/java.lang=ALL-UNNAMED -jar app.jar
```

3. **JDK 17 默认强封装**：`--illegal-access` 已失效，任何未开放的跨模块反射都会被拒。很多老框架（旧版 Hibernate、低版本 Jackson、部分序列化库）升级 JDK 17 后报错，根因就在这里。

面试延伸：**这也是为什么「反射能改 final 常量」在 JDK 17 上并不可靠** —— 基本类型 `static final` 在编译期已内联进调用方字节码，改了也读不到新值。

## 七、反射为什么慢？怎么优化？（★★★★★ 高分题）

### 四个原因

| 原因 | 说明 |
| --- | --- |
| 无法 JIT 内联 | 常规方法调用能被 JIT 内联、常量折叠；反射调用要经过 `Method.invoke` 的通用入口，难以优化 |
| 参数封装与拆箱 | `invoke(Object obj, Object... args)` 每次都要把参数装进 Object 数组，基本类型要装箱 |
| 访问权限检查 | 每次调用都做可见性校验（`setAccessible(true)` 可规避） |
| 方法动态解析 | 运行期遍历方法表匹配签名，`getMethod` 不缓存的话开销更大 |

JDK 8 之后有个 **inflation 机制**：同一个 `Method` 累计调用超过阈值（默认 15 次，`-Dsun.reflect.inflationThreshold`）后，会动态生成字节码来执行，性能接近直接调用。所以**反射并非一直慢，慢的是「首次 + 高频重复查找」**。

### 五个优化手段

1. **缓存** `Class` / `Method` / `Field` / `Constructor`（收益最大，框架都这么干）
2. `setAccessible(true)` 跳过权限检查
3. 改用 **`MethodHandle`**（JDK 7+），可被 JIT 内联，性能介于反射和直接调用之间
4. 追求极致用 **`LambdaMetafactory` / 字节码生成**（CGLIB、ASM、ByteBuddy）
5. 避免在循环里反复 `getDeclaredMethod`，把查找提到循环外

```java
// 缓存示例：Spring 的 ReflectionUtils 就是这个思路
private static final Map<String, Method> METHOD_CACHE = new ConcurrentHashMap<>();

public static Object invokeCached(Object target, String methodName) throws Exception {
    Class<?> cls = target.getClass();
    String key = cls.getName() + "#" + methodName;
    Method m = METHOD_CACHE.computeIfAbsent(key, k -> {
        try {
            Method mm = cls.getDeclaredMethod(methodName);
            mm.setAccessible(true);
            return mm;
        } catch (NoSuchMethodException e) {
            throw new IllegalStateException(e);
        }
    });
    return m.invoke(target);
}
```

```java
// MethodHandle：性能更好的反射替代，注意 invokeExact 要求签名完全精确
MethodHandles.Lookup lookup = MethodHandles.lookup();
MethodHandle mh = lookup.findVirtual(Cat.class, "hi", MethodType.methodType(void.class));
mh.invoke(cat);
```

**实测口径**：同一次调用重复一百万次，直接调用最快，`MethodHandle` 次之，`Method.invoke` 慢一个数量级左右（量级会随 JDK 版本和预热情况变化，答题时说「一个数量级以上」足够）。

## 八、优缺点（面试要求「客观评价」）

| 优点 | 缺点 |
| --- | --- |
| 运行期动态操作，解耦、可配置 | 性能开销大（解释执行/装箱/检查） |
| 框架基石：容器、AOP、ORM 都依赖它 | 破坏封装，可访问私有成员 |
| 能处理编译期未知的类型 | 编译期无检查，错误要运行期才暴露 |
| 注入注解、驱动插件机制 | 代码可读性差，IDE 无法跳转重构 |

结论：**业务代码尽量别用，框架和工具类里必须用。**

| 场景 | 反射用来做什么 |
| --- | --- |
| Spring IOC/DI | 扫描注解、`newInstance` 创建 Bean、给字段/构造器注入依赖 |

| JUnit / TestNG | 扫描 `@Test` 方法并反射调用 |

## 十、反射与类加载（★★★ 深挖题）

类加载三阶段：**加载 → 链接（验证/准备/解析）→ 初始化**。`Class.forName` 与 `ClassLoader.loadClass` 的差别就在最后这一步：

- `Class.forName(name)` → 加载 + 链接 + **初始化**（执行 `<clinit>`，即静态代码块）
- `ClassLoader.loadClass(name)` → 只做加载 + 链接，**不初始化**（懒加载）

触发类初始化的六种时机（面试可背）：`new` 实例、访问静态字段/方法、反射 `forName`、初始化子类会先初始化父类、`main` 所在类、`MethodHandle` 解析。

另外记住**双亲委派**的后果：同一个类被不同类加载器加载，会产生两个不同的 `Class` 对象，`instanceof` 判定失败、强转抛 `ClassCastException`。热部署、Tomcat 多应用场景的诡异问题大多源于此。

## 十一、反射的最佳搭子：动态代理（★★★★ 常考）

动态代理的调用链本质就是反射：代理对象拦截方法调用 → 交给 `InvocationHandler` → 在 handler 里用 `method.invoke(target, args)` 调用真实对象。

```java
interface UserService {
    void save(String name);
}

class UserServiceImpl implements UserService {
    public void save(String name) { System.out.println("保存 " + name); }
}

public class ProxyDemo {
    public static void main(String[] args) {
        UserService target = new UserServiceImpl();

        UserService proxy = (UserService) Proxy.newProxyInstance(
                target.getClass().getClassLoader(),
                target.getClass().getInterfaces(),
                (p, method, a) -> {
                    System.out.println("前置增强：开启事务");
                    Object result = method.invoke(target, a);   // 反射调用真实方法
                    System.out.println("后置增强：提交事务");
                    return result;
                });

        proxy.save("张三"); // 事务逻辑会自动织入
    }
}
```

| | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 前提 | 目标类**必须实现接口** | 通过继承生成子类，无需接口 |
| 实现 | `Proxy` + `InvocationHandler`，反射调用 | ASM 生成字节码，直接调用（不走反射） |
| 限制 | 只能代理接口中声明的方法 | `final` 类、`final` 方法不能代理 |
| 性能 | JDK 8+ 已接近 CGLIB | 创建慢、执行快 |
| Spring AOP | 有接口时默认用 | 无接口时用；`proxyTargetClass=true` 可强制 |

Spring Boot 2.x 起默认 `proxyTargetClass=true`，也就是说**默认走 CGLIB**。

## 十二、反射能破坏单例（面试脑筋题 + 防御）

```java
class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}

// 反射破解
Constructor<Singleton> ctor = Singleton.class.getDeclaredConstructor();
ctor.setAccessible(true);
Singleton s1 = ctor.newInstance();
Singleton s2 = ctor.newInstance();
System.out.println(s1 == s2); // false，单例被破坏
```

三种防御：

1. 构造器内判断，已存在实例就抛异常（要防住反射还需加标志位）
2. **枚举单例天然免疫**：`Constructor.newInstance` 对枚举类型直接抛 `IllegalArgumentException`，也是《Effective Java》推荐写法
3. 用 `readResolve()` 防序列化破坏（反射仍可破，枚举不受影响）

## 十三、常见异常与坑（★★★★ 排查用）

| 异常 / 现象 | 原因 | 解法 |
| --- | --- | --- |
| `ClassNotFoundException` | 全限定名写错 / 类不在 classpath | 检查包名、依赖是否引入 |
| `NoSuchMethodException` | 方法私有却用了 `getMethod`，或参数类型不匹配 | 改 `getDeclaredMethod`，参数写精确类型 `int.class` |
| `IllegalAccessException` | 访问了非 public 成员 | 先 `setAccessible(true)` |
| `InstantiationException` | 抽象类/接口/无无参构造 | 用 `getDeclaredConstructor(...)` 指定参数 |
| `InvocationTargetException` | **目标方法自己抛了异常**，被包了一层 | `e.getCause()` 或 `getTargetException()` 取真实异常 |
| `InaccessibleObjectException` | JDK 9+ 模块限制 | 启动参数 `--add-opens` |
| 参数类型不匹配 | `getMethod("set", Integer.class)` 找不到 `set(int)` | 用 `int.class`，基本类型与包装类不通用 |
| 静态成员 invoke 报 NPE 以外的问题 | 传了对象而非 `null`，或反之 | 静态方法/字段的对象参数传 `null` |

## 十四、面试速答清单

| 问题 | 一句话答案 |
| --- | --- |
| 反射是什么？ | 运行期获取并操作类结构的能力，核心是 Class 对象 |
| 获取 Class 的四种方式？ | `类名.class`（不初始化）、`对象.getClass()`、`Class.forName`（初始化）、`loadClass`（不初始化） |
| forName 和 loadClass 区别？ | 前者走完整初始化（执行静态块），后者只加载链接 |
| getMethod 和 getDeclaredMethod 区别？ | 前者只 public 且含继承，后者含私有但只看本类 |
| 反射为什么慢？ | 无法内联、参数装箱、权限检查、动态解析方法 |
| 怎么优化？ | 缓存 Method、`setAccessible`、MethodHandle、字节码生成 |
| 反射能拿泛型吗？ | 能拿声明处的泛型（字段/参数/父类），拿不到运行时的实际类型参数 |
| 反射能改 final 字段吗？ | 语法上可以，但 `static final` 基本类型已被编译期内联，改了读不到 |
| Spring 哪里用了反射？ | IOC 创建 Bean 与依赖注入、AOP 代理调用、注解解析 |
| 反射如何破坏单例？怎么防？ | 私有构造 `setAccessible` 后 new 两次；用枚举单例或构造器校验 |

## 十五、顺手记一个高频延伸：泛型信息获取

```java
class Result<T> {
    private List<String> names;              // 字段上的泛型能拿到
    public void set(List<Integer> nums) {}   // 方法参数的泛型能拿到
}

Field f = Result.class.getDeclaredField("names");
ParameterizedType pt = (ParameterizedType) f.getGenericType();
System.out.println(pt.getActualTypeArguments()[0]); // class java.lang.String
```

能拿到的是**声明处写死的泛型**（字段、方法签名、父类），拿不到 `new ArrayList<String>()` 这种运行期已被擦除的实际类型 —— 这也是为什么 Spring 能用 `@Autowired` 注入 `List<UserService>` 这类集合（靠签名上的泛型信息），而 `new ArrayList<>()` 的泛型在运行时是拿不到的。

**dev / 学习提示**：反射代码调试时优先看 `InvocationTargetException.getCause()` 的堆栈，真实异常往往被这层包装藏住；升级 JDK 17 时若报 `InaccessibleObjectException`，先查是不是框架在反射 JDK 内部类，用 `--add-opens` 临时放开，长期方案是升级框架版本。
